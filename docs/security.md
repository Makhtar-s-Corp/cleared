# Security boundaries

## Release lock threat model

A ticket, web page, pull request, review, or comment can contain instructions that mislead any agent harness. An agent may then ask to publish without approval, forge or replay a validation file, substitute another PR or commit, or invoke a merge script directly. Agent output and request fields never identify a human.

The service account owns Cleared's state, validation records, ledger, release checkout, and Unix socket. Agent processes run as the distinct `[security] agent_user`; they can edit their team worktrees and call the socket, but cannot write service state, change the service executable, its configuration, or the main checkout. The kernel's peer UID identifies the caller. The service obtains human identity and the timing of approval from the configured tracker contract. It independently checks the shown PR and commit, review verdict, green CI, and active release watch immediately before merging, under a single merge lock. Every request is logged with UID, result, reason, and commit. The service account and host administrator remain trusted.

A writable validation file is not an authority: the tracker supplies the human action. A validation record only binds the request time and the shown PR and commit; it must be written by the service account when the request is posted. Because the current tracker contracts may authenticate an integration as a person, installations that cannot distinguish owner actions from agent actions must retain the existing `separate_identity` refusal.

Without `[security] agent_user`, both harnesses run with the service account's filesystem rights. The service still performs its checks, but filesystem isolation is absent. `cleared status` must report: “release lock is not a security boundary: agents run as the service account”. Do not treat harness allow lists, prompts, or a Codex sandbox as the security boundary.

The socket is local only. Its parent directory permits the configured agent account to connect, and peer UID checks deny unrelated users. Codex needs access to this socket path; the Linux sandbox may fail to mount a socket. Use the documented host fallback under the agent UID in that case. Never expose the broker on a TCP port.


Cleared is alpha software that can read source code, create pull requests, and, after approval, merge them. Run it on a host and repository you control. Claude Code and Codex run on that host. Configure `[security] agent_user` to run both harnesses under a separate account. For stronger isolation, run Cleared under a dedicated operating-system account without other projects' secrets.

An automatic rollback is a direct, ordinary push of a revert commit to the configured base branch after repeated health failures. It reverts only the recorded two-parent merge commit; a conflict or a moved base makes the push fail without force. Manual rollback requires the configured human owner's verified tracker or local account identity. `--yes` skips only the prompt. If the merge touched configured migration paths, automatic rollback is refused and manual rollback needs `--force-with-migrations`; Cleared never undoes database schema or data migrations. Branch protection and repository credentials must be configured so the rollback identity can push a revert, or the operation fails and alerts the owner. Health commands run with the Cleared account's permissions, so configure only trusted commands.

When `auto_rollback = true`, application code can make a health probe fail and thereby cause Cleared to revert the release without another human decision. This is the intended emergency action after a previously approved merge. Keep the health endpoint and `[release]` settings under owner review; do not make the probe depend on untrusted scripts or remote responses. A different commit appearing on the base after the release prevents automatic rollback, even if the revert would apply cleanly.

## Identities and approval

The ticket owner and the agent need separate identities. The Linear adapter prefers `LINEAR_APP_CLIENT_ID` and `LINEAR_APP_CLIENT_SECRET` for an agent application, with a short-lived token kept under the state directory. `LINEAR_API_KEY` can be used to explore and open a test team, but `[merge] separate_identity = required` blocks unattended shipping when Cleared cannot distinguish the agent from the ticket owner. Store credentials in environment variables or an untracked `.env.local`; the scripts read only the values they need. The Claude adapter removes `ANTHROPIC_API_KEY` and the Codex adapter removes `OPENAI_API_KEY` so subscription sessions do not silently switch to API billing. Both model adapters remove the known tracker and GitHub token variables before starting the CLI; keep other project secrets out of that environment. Authenticate `gh`, Claude Code, and/or Codex separately. Never put credentials in `agents.conf`, a prompt, a ticket, or a pull request.

For GitHub Issues, configure a GitHub App private key so Cleared can obtain short-lived installation tokens, and use the human account for approval. Keep the key outside the repository with mode `0600`. A harness running without `agent_user` can still read that key; limit the App to the intended repositories and permissions. Local SQLite requires separate system accounts and signed human actions; see [Ticket trackers](trackers.md). A personal GitHub token or one shared system account cannot prove an approval.

For application and guarded paths, the broker runs `merge-pr.sh`, which checks a reviewed commit, successful checks, the owner's own ticket move to the configured go state, and the exact version previously shown. A change touching only configured `[merge] tooling_paths` skips the ticket approval check, but still needs review and green checks. Keep that list narrow and protect the base branch in GitHub; a person with direct merge rights can bypass Cleared. The script serializes merges under a lock and rechecks before shipping. When code or a conflict resolution changes the approved version, ask again. A clean merge of the base that adds no team code can keep approval.

## Private-term guard

The guard scans text and diffs sent to an external ticket tracker or GitHub, including comments, pull requests, and commits, when they pass through Cleared scripts, regardless of which harness authored them. It does not filter instructions sent to either model. Direct CLI or network calls from a model bypass this scan; protect forge and tracker credentials outside model command access and use branch protection. It compares normalized words against SHA-256 fingerprints of project-specific private terms. `[guard] salt` must be committed in the **project's** `.cleared/agents.conf` alongside the configured fingerprint lists; installation never writes a salt. Lists include a short identifier derived from that salt. When lists are configured, a missing or mismatched salt makes the guard refuse all text until the correct salt is committed or the lists are rebuilt. Lists without an identifier are also refused. Fingerprint lists named by `[guard] terms` and `allowed` live in the project and are read from its remote base branch, not from the working team's editable files. If both list keys are omitted or set to `none`, private-term matching is disabled and one ledger event records it; generic secret checks still run. The guard also checks common secret and sensitive-data patterns and rejects text it cannot read safely.

To build a list, first commit a random `[guard] salt` and set `[guard] terms = scripts/private-terms.json` in the project config. Keep the plain-text input outside the project checkout. From the project checkout, run `CLEARED_REPO=$PWD node ../cleared/lib/guard/private-terms.mjs hash < /path/outside/project/private-terms.txt > scripts/private-terms.json`, replacing `../cleared` with your Cleared checkout path. The command writes JSON with `salt_id` and hashes. Commit and push the JSON file before enabling the list. Set `ORCH_GUARD_REF=HEAD` for this command only if the committed config has not reached `origin/main` yet; the running guard reads the remote ref. Never commit the plain-text input.

GitHub capture publishing runs OCR and the text guard before pushing image bytes to a dedicated branch. OCR can miss visual secrets; only use demo-data captures that a person inspected. The capture branch retains images in Git history.

A fingerprint list is a screening rule, not encryption or a guarantee against disclosure. It cannot catch terms that were never listed, encoded or transformed data, or every form of secret. A model or process with unrestricted network or file access can bypass text scanning; isolate it with host permissions, containers, and repository rules appropriate to your project. Do not copy real private terms into this tool repository.

## Permissions and host access

`[permissions.<role>]` maps role intent to each provider CLI. Claude receives command prefixes; Codex receives filesystem and network sandbox settings. Neither offers exactly the same controls as the other. Codex hides common credential stores from sandboxed commands, but both harnesses may read other files available to the Cleared account. Development roles need network access for TCP test databases, so they can also contact external destinations unless the host enforces a separate network policy. The release role calls the broker over a Unix socket. With `agent_user`, filesystem ownership prevents both harnesses from writing approval state. Cleared mounts the shared Git control directory and each team's `.git` entry read-only around either harness; the dispatcher commits changes after a session. See the [role table](adapters.md#existing-adapters). The project lead and reviewer should be read-only; development roles may edit their own worktrees. `when-free.sh` gates commands that compete for host resources, such as screen tests. This is scheduling, not isolation. Dependencies from the base lock file are installed by the dispatcher with `npm ci --ignore-scripts`; a team's new dependency waits for CI after its pull request. Review CI and deployment workflows as carefully as code: `[merge] guarded_paths` should include them and the Cleared lock scripts.

The optional dashboard contains ticket titles and host status. `serve/install.sh` binds it to the host's Tailscale address and verifies that only the page is served. Configure network access separately; `serve/check.sh` can also probe from an existing container when `CLEARED_CHECK_CONTAINER` is set. The read-only [Cleared app](app.md) is held to the same checks on its own port and also needs an access token: it reads only, shows no money amount, and its token file is private and outside the project. No container is required for the normal check. State and tokens are kept outside the repository under `~/.local/state/cleared/<project>/`; limit filesystem access to that directory.

## Reporting a vulnerability

Use the private GitHub vulnerability report described in [SECURITY.md](../SECURITY.md). Do not post exploit details, credentials, or private project data in a public issue. The scope includes approval and merge checks, identity checks, adapters, guard bypasses, the dashboard, state and token handling, and installation scripts.

## Installing the release account boundary

The installer does not create a system account. An administrator must create an unprivileged account (for example `cleared-agents`) with its own Claude Code and Codex login, set `[security] agent_user = cleared-agents` in the tracked project configuration, and set `[security] socket_path` to an absolute Unix socket path reachable from that account. Install bubblewrap at `/usr/bin/bwrap` or set `[security] bwrap_path` to its executable. Give the service account passwordless, noninteractive `sudo -u cleared-agents` for launching the harness CLIs and the installer’s UID, socket, and write probes; do not grant the reverse direction. The target account needs a PATH containing its own `.local/bin` so both CLIs can start. Do not give it GitHub merge or push credentials, the tracker owner key, or the service’s token files. Keep the Cleared checkout, the project's main checkout, `.cleared/agents.conf`, and the state tree owned by the service account. Give the agent account traversal and read access to the tool checkout and tracked project configuration without write; service home directories often default to mode `0700`, so add an explicit ACL on those paths. Give the agent account write access only to team worktrees and its CLI home. If it must read selected state files, grant read and directory traversal without write using ACLs. Verify both `sudo -n -u cleared-agents -- id -un` and `sudo -n -u cleared-agents -- test ! -w <Cleared state directory>` before enabling the broker.

The socket needs a service-owned parent directory that the agent account can traverse. Give the socket parent execute permission to the agent account and set the socket path in the tracked configuration; the broker checks peer UID using Linux `SO_PEERCRED` and rejects every UID except the service and configured agent. The Node service uses Python 3's standard library solely to read `SO_PEERCRED` because Node's Unix socket API does not expose it. No npm dependency or network listener is added. On the Linux host used for this change, Codex 0.162.1 failed before starting the agent because bubblewrap tried to mount the Unix socket as a regular file. An unsandboxed host Codex probe reached the socket. Because the sandbox could not connect, the Codex release role uses the host runner without its filesystem sandbox when `agent_user` is configured; the operating-system account boundary still denies state writes. Bubblewrap is used around team sessions to protect shared Git metadata, but not around the release lead: bubblewrap sets `NoNewPrivs`, which blocks its narrow sudo bridge, and the lead runs from the service-owned main checkout. Check both harnesses on the actual server before relying on the lock. The installer refuses a configured `agent_user` if it can write the state directory or main checkout.

The agent asks for approval through `release-request.mjs request_release TICKET PR --ask` and later calls `release-request.mjs request_release TICKET PR` with the announcement on standard input. The broker writes the request record and checks the tracker action; the agent never writes a validation record. The existing `cleared rollback` command routes through the same broker. An agent rollback requires a fresh owner comment ID in the tracker. Socket access alone does not authorize a release or rollback.

The lead's existing review and communication commands also need service-owned state and tracker credentials. `lead-command.mjs` uses a second, narrow `sudo` rule to invoke `serve/lead-actions.mjs` as the service account. The wrapper accepts only review, tracker read/comment/create, team message, host status, and digest actions; it has no merge, approval-state edit, tracker move, or arbitrary command action. Configure sudoers for the agent account to run exactly `/usr/bin/node <absolute Cleared checkout>/serve/lead-actions.mjs *` as the service account without a password, with `env_reset`; do not grant the agent account general sudo to the service account. The installer probes this route. A project-owned release prompt that still names the old direct scripts must be updated to the broker and lead client commands before enabling the split account.

For example, an administrator can create the account with `sudo useradd --create-home --shell /bin/bash cleared-agents`, and create a service-owned socket directory with `sudo install -d -o cleared-service -g cleared-service -m 0711 /srv/cleared-run`. Set `socket_path = /srv/cleared-run/release.sock` in the tracked config. Replace `cleared-service` with the actual account running the user systemd units. A sudoers file edited with `visudo` can grant `cleared-service ALL=(cleared-agents) NOPASSWD: ALL` and `cleared-agents ALL=(cleared-service) NOPASSWD: /usr/bin/node /absolute/path/to/cleared/serve/lead-actions.mjs *`. Keep `env_reset` enabled. Give `cleared-agents` read and traversal ACLs on the Cleared checkout and main project, and write ACLs on team worktrees only. Authenticate Claude and Codex in the new account. Run `serve/install.sh` again: it checks the account UID, tries to create a file in state as the agent (which must fail), scans for writable protected paths, probes the lead wrapper, and connects to the socket as the agent.
