# Security boundaries

## Release lock threat model

A ticket, web page, pull request, review, or comment can contain instructions that mislead any agent harness. An agent may then ask to publish without approval, forge or replay a validation file, substitute another PR or commit, or invoke a merge script directly. Agent output and request fields never identify a human.

The service account owns Cleared's state, validation records, ledger, release checkout, and Unix socket. Agent processes run as the distinct `[security] agent_user`; they can edit their team worktrees and call the socket, but cannot write service state, change the service executable, its configuration, or the main checkout. The kernel's peer UID identifies the caller. The service obtains human identity and the timing of approval from the configured tracker contract. It independently checks the shown PR and commit, review verdict, green CI, and active release watch immediately before merging, under a single merge lock. Every request is logged with UID, result, reason, and commit. The service account and host administrator remain trusted.

A writable validation file is not an authority: the tracker supplies the human action. A validation record only binds the request time and the shown PR and commit; it must be written by the service account when the request is posted. Because the current tracker contracts may authenticate an integration as a person, installations that cannot distinguish owner actions from agent actions must retain the existing `separate_identity` refusal.

Without `[security] agent_user`, both harnesses run with the service account's filesystem rights. By default the broker refuses release requests and manual rollback requests. Create a separate unprivileged agent account, set `[security] agent_user` to its name, give it access to team worktrees and the socket but no write access to Cleared state, then run `serve/install.sh`. To retain the older shared-account behavior, explicitly set `[security] allow_shared_uid = true` in the tracked configuration. This permits releases and manual rollback but cannot distinguish an agent from the service or human account. `cleared status` permanently reports: “release lock is not a security boundary: agents run as the service account”. Do not treat harness allow lists, prompts, or a Codex sandbox as the security boundary.

The socket is local only. Its parent directory permits the configured agent account to connect, and peer UID checks deny unrelated users. Codex needs access to this socket path; the Linux sandbox may fail to mount a socket. Use the documented host fallback under the agent UID in that case. Never expose the broker on a TCP port.

The single agent UID covers all agent roles. A prompt-injected coding session can request approval, ask for a release, or use the narrow lead-action bridge. These calls do not identify a human and cannot authorize release; the tracker contract and service-owned run ledger supply that evidence. Role prompts and command lists remain workflow guidance, not an OS boundary between agents. Keep forge merge credentials and the tracker owner's credentials outside the agent account, and enforce branch protection on the base branch.


Cleared is alpha software that can read source code, create pull requests, and, after approval, merge them. Run it on a host and repository you control. Claude Code and Codex run on that host. Configure `[security] agent_user` to run both harnesses under a separate account. For stronger isolation, run Cleared under a dedicated operating-system account without other projects' secrets.

An automatic rollback is a direct, ordinary push of a revert commit to the configured base branch after repeated health failures. It reverts only the recorded two-parent merge commit; a conflict or a moved base makes the push fail without force. Manual rollback requires `cleared rollback` from the configured human Unix account; the broker checks its peer UID. A tracker comment cannot authorize rollback. `--yes` skips only the prompt. If the merge touched configured migration paths, automatic rollback is refused and manual rollback needs `--force-with-migrations`; Cleared never undoes database schema or data migrations. Branch protection and repository credentials must be configured so the rollback identity can push a revert, or the operation fails and alerts the owner. Health commands run with the Cleared account's permissions, so configure only trusted commands.

When `auto_rollback = true`, application code can make a health probe fail and thereby cause Cleared to revert the release without another human decision. This is the intended emergency action after a previously approved merge. Keep the health endpoint and `[release]` settings under owner review; do not make the probe depend on untrusted scripts or remote responses. A different commit appearing on the base after the release prevents automatic rollback, even if the revert would apply cleanly.

## Fast lane

The [fast lane](fast-lane.md) spares waits for a tiny change, never a gate: green full checks on the exact commit, a review by another model and the human's agreement to that version still bind every merge. Its decision comes from rules over the real diff at one commit, with the settings of the main checkout; it is kept in service-owned state, recomputed by `merge-pr.sh` at the merged commit, and refused to any account but the state's owner. A pull request that touches `.cleared/`, CI, agent rules, dependencies, migrations or `[merge] guarded_paths` is never fast. Its targeted tests run the branch's code: under `[security] agent_user` they run as that account in the agents' sandbox, with an empty environment and no shell.

## Branch protection

Cleared's merge lock only binds those who go through it. A person or a token with permission to push to the base branch, or to merge a pull request directly, bypasses every check described here. Enable branch protection (or a repository ruleset) on the base branch: require a pull request, and do not give the agents' accounts or any credential they can reach a bypass.

GitHub offers branch protection and rulesets on **private repositories only with a paid plan** (GitHub Pro, Team or Enterprise). **A private repository on a free plan cannot be protected**: the API answers `403 Upgrade to GitHub Pro or make this repository public to enable this feature`. Cleared cannot detect the gap from the outside, so on such a repository the lock is advisory for whoever holds a credential with write access: keep that credential in the service account only, and treat any direct push to the base branch as outside Cleared. Automatic rollback pushes a revert directly to the base branch, so with branch protection enabled the rollback identity must be allowed to bypass the pull request requirement.

## Identities and approval

The ticket owner and the agent need separate identities. The Linear adapter prefers `LINEAR_APP_CLIENT_ID` and `LINEAR_APP_CLIENT_SECRET` for an agent application, with a short-lived token kept under the state directory. `LINEAR_API_KEY` can be used to explore and open a test team, but `[merge] separate_identity = required` blocks unattended shipping when Cleared cannot distinguish the agent from the ticket owner. Store credentials in environment variables or an untracked `.env.local`; the scripts read only the values they need. The Claude adapter removes `ANTHROPIC_API_KEY` and the Codex adapter removes `OPENAI_API_KEY` so subscription sessions do not silently switch to API billing. Both model adapters remove the known tracker and GitHub token variables before starting the CLI; keep other project secrets out of that environment. Authenticate `gh`, Claude Code, and/or Codex separately. Never put credentials in `agents.conf`, a prompt, a ticket, or a pull request.

For GitHub Issues, configure a GitHub App private key so Cleared can obtain short-lived installation tokens, and use the human account for approval. Keep the key outside the repository with mode `0600`. A harness running without `agent_user` can still read that key; limit the App to the intended repositories and permissions. Local SQLite requires separate system accounts and signed human actions; see [Ticket trackers](trackers.md). A personal GitHub token or one shared system account cannot prove an approval.

Forge credentials follow the same rule. Without [`[forge]`](configuration.md#forge), pushes, pull requests and merges use the `gh` login and git credentials of the service account. With a GitHub App configured there (or, with `[forge] use_tracker_app = yes`, the GitHub Issues tracker's app, used for both), they use the app instead: its private key lives with the service account only, outside the repository, mode `0600`; Cleared mints installation tokens that last one hour, keeps the current one in the service-owned state (mode `0600`), and hands it to `gh` for one call or to git through a credential helper, never in a command line, the ledger, a log or an error message. The agents' account has no forge credential: the model adapters remove the token variables, the credential helper settings and the dispatcher's commit identity before a harness starts, and under `agent_user` it can read neither the key nor the token (`serve/install.sh` probes both as that account). Pull requests, pushes, merges and the dispatcher's commits then show as the app's bot, so GitHub's own history tells them from the human's. A configured app that cannot give a token stops forge calls instead of falling back to the ambient credential. Give the installation only the permissions listed in [the configuration reference](configuration.md#forge). The app does not replace the human's own accesses: the owner still needs their own GitHub account (and the tokens of [the app's human writes](#the-app-acts-as-the-human)) to review, approve and administer the repository. A harness running without `agent_user` can read the key like any file of the service account. Do not set `GH_DEBUG`, `GIT_TRACE`, `GIT_TRACE_CURL` or `GIT_CURL_VERBOSE` in the service environment: they make `gh` and git print request headers, including `Authorization`, into run logs and terminal output. With a GitHub App the scripts remove them wherever the token can be used, but other tools of the service account would still honour them.

**Upgrade note:** the forge identity is opt-in. An existing installation, including one that tracks tickets in GitHub Issues with an app, keeps pushing and merging with the service account's own credentials until `[forge]` names an app or says `use_tracker_app = yes`. Before switching, grant the installation the [permissions each feature needs](configuration.md#forge) and add `app_user_id`; `cleared status` then shows `as <app login>` on the forge line.

For application and guarded paths, the broker runs `merge-pr.sh`, which checks a reviewed commit, successful checks, the owner's own ticket move to the configured go state, and the exact version previously shown. A change touching only configured `[merge] tooling_paths` skips the ticket approval check, but still needs review and green checks. Keep that list narrow and protect the base branch in GitHub; a person with direct merge rights can bypass Cleared. The script serializes merges under a lock and rechecks before shipping. When code or a conflict resolution changes the approved version, ask again. A clean merge of the base that adds no team code can keep approval.

## Private-term guard

The guard scans text and diffs sent to an external ticket tracker or GitHub, including comments, pull requests, and commits, when they pass through Cleared scripts, regardless of which harness authored them. It does not filter instructions sent to either model. Direct CLI or network calls from a model bypass this scan; protect forge and tracker credentials outside model command access and use branch protection. It compares normalized words against SHA-256 fingerprints of project-specific private terms. `[guard] salt` must be committed in the **project's** `.cleared/agents.conf` alongside the configured fingerprint lists; installation never writes a salt. Lists include a short identifier derived from that salt. When lists are configured, a missing or mismatched salt makes the guard refuse all text until the correct salt is committed or the lists are rebuilt. Lists without an identifier are also refused. Fingerprint lists named by `[guard] terms` and `allowed` live in the project and are read from its remote base branch, not from the working team's editable files. If both list keys are omitted or set to `none`, private-term matching is disabled and one ledger event records it; generic secret checks still run. The guard also checks common secret and sensitive-data patterns and rejects text it cannot read safely.

To build a list, first commit a random `[guard] salt` and set `[guard] terms = scripts/private-terms.json` in the project config. Keep the plain-text input outside the project checkout. From the project checkout, run `CLEARED_REPO=$PWD node ../cleared/lib/guard/private-terms.mjs hash < /path/outside/project/private-terms.txt > scripts/private-terms.json`, replacing `../cleared` with your Cleared checkout path. The command writes JSON with `salt_id` and hashes. Commit and push the JSON file before enabling the list. Set `ORCH_GUARD_REF=HEAD` for this command only if the committed config has not reached `origin/main` yet; the running guard reads the remote ref. Never commit the plain-text input.

GitHub capture publishing runs OCR and the text guard before pushing image bytes to a dedicated branch. OCR can miss visual secrets; only use demo-data captures that a person inspected. The capture branch retains images in Git history.

A fingerprint list is a screening rule, not encryption or a guarantee against disclosure. It cannot catch terms that were never listed, encoded or transformed data, or every form of secret. A model or process with unrestricted network or file access can bypass text scanning; isolate it with host permissions, containers, and repository rules appropriate to your project. Do not copy real private terms into this tool repository.

## Permissions and host access

`[permissions.<role>]` maps role intent to each provider CLI. Claude receives command prefixes; Codex receives filesystem and network sandbox settings. Neither offers exactly the same controls as the other. Codex hides common credential stores from sandboxed commands, but both harnesses may read other files available to the Cleared account. Development roles need network access for TCP test databases, so they can also contact external destinations unless the host enforces a separate network policy. The release role calls the broker over a Unix socket. With `agent_user`, filesystem ownership prevents both harnesses from writing approval state. Cleared mounts the shared Git control directory and each team's `.git` entry read-only around either harness; the dispatcher commits changes after a session. The default `dev` prompt then tells the team not to try to commit, to leave its commit message in `.commit-message`, and not to report the refused commit as a block; without `agent_user` it still tells the team to commit. A project's own `.cleared/prompts/<role>.md` gets the same two texts by writing the `@COMMIT_RULE@` and `@COMMIT_INDEPENDENT@` placeholders where the default prompt has them. See the [role table](adapters.md#existing-adapters). The project lead and reviewer should be read-only; development roles may edit their own worktrees. `when-free.sh` gates commands that compete for host resources, such as screen tests. This is scheduling, not isolation (see [the door of the heavy commands](#the-door-of-the-heavy-commands)). Dependencies from the base lock file are installed by the dispatcher with `npm ci --ignore-scripts`; a team's new dependency waits for CI after its pull request. Review CI and deployment workflows as carefully as code: `[merge] guarded_paths` should include them and the Cleared lock scripts.

Stopping a session ends what it started, whatever account runs it. Under `agent_user`, bubblewrap runs with `--die-with-parent --unshare-pid --proc /proc`: the sandbox has its own process namespace, and when sudo, its parent, ends, the kernel ends every process in it, including one that left the harness's process group. With `[terminal] adapter = none`, closing a session also signals its process group as the agents' account, sends SIGKILL after a grace period, and checks that nothing of the group is left; if something is, the failure is printed and recorded and the worktree stays (see [`[terminal]`](configuration.md#terminal)). The acting lead runs without bubblewrap (below): under `none`, the process-group signal reaches it and everything still in its group, but not a process it moved into a session of its own. Under Orca, closing a terminal sends a hangup that sudo passes on to the command it runs; that ends a sandbox, and for the unsandboxed acting lead nothing more is done. If `/proc` is mounted with `hidepid`, the service cannot see the agents' processes: the agents' account is then asked through sudo, also for a session whose run script already died, and a close it cannot confirm fails instead of reporting success.

The optional dashboard contains ticket titles and host status. `serve/install.sh` binds it to the host's Tailscale address and verifies that only the page is served. Configure network access separately; `serve/check.sh` can also probe from an existing container when `CLEARED_CHECK_CONTAINER` is set. The [Cleared app](app.md) is held to the same checks on its own port and also needs an access token: it shows no money amount, and its token file is private and outside the project. Its writes are described next. No container is required for the normal check. State and tokens are kept outside the repository under `~/.local/state/cleared/<project>/`; limit filesystem access to that directory.

## The door of the heavy commands

Heavy commands (screen tests, captures), the checks the rules start and a host Codex session hold one lock, so that they do not run at the same time on the host. The lock is a file held with `flock`. `flock` takes an exclusive lock on a descriptor opened for reading only, so the agents' account opens the file read-only and needs no write access to it. The service, which may write the file, opens it for writing, as before.

Under `[security] agent_user`, the teams cannot open a file in the service-owned state, and they must not be able to. Set [`[lanes] heavy_lock`](configuration.md#lanes) to a file outside the state, in a directory owned by the service that the agents' account can traverse but not write. `serve/install.sh` creates the file with mode `0644`. It proves, as the agents' account, that the account can open the file read-only and take the lock, and that it can write neither the file, its directory, nor any directory above it (one it could write would let it put a lock and a status of its own in place of that directory). Do not put the lock under a world-writable directory such as `/tmp`. The agents' account gets no new write access anywhere.

A team also cannot ask GitHub or read the state to know whether the host is free. The service writes a small status file next to the lock instead, at every wake, when the rules start checks and when a merge starts. The team reads that file and never calls `gh` or `sudo`. It holds booleans and two times, with no ticket text, branch, path or credential, and it is readable by every local account. A status older than 2 minutes or that cannot be read counts as "not free": `when-free.sh` runs nothing and ends with exit 5, and a missing one ends it at once. This is looser than asking the host live: a push or a deployment started outside Cleared since the last write is not seen for up to 2 minutes. `host-state.sh` and the lead's `lead-command.mjs host` are unchanged.

What the lock gives the agents' account:

- **Denial of service only.** A team that holds the lock, through `when-free.sh` running a long command or by opening the file and calling `flock` itself, delays the checks of every pull request (`flow-lanes.sh` does not take a pull request out of draft while the lock is held), host Codex sessions and the other teams' heavy commands. Each waiting team gives up after `[lanes] heavy_wait_minutes` with exit 5, and a Codex session reports "cannot start now". Stopping the session releases the lock: closing a session ends every process in its sandbox. `lslocks` (or `/proc/locks`) shows which process holds it.
- **No bypass of approval.** The lock grants nothing. It does not approve, merge, push or write any record, and holding it or leaving it free changes nothing that the release broker checks. A team can also skip the lock: it can run `npm run test:ui` directly, or set `CLEARED_HEAVY_SLOT` to the lock's path. The lock is scheduling for cooperating sessions, as `when-free.sh` always was, not a boundary.
- **The status file is the service's.** The agents' account cannot write the status file or the lock's directory, so it cannot make the host look free to another team.

## The app acts as the human

The [Cleared app](app.md) can clear a ticket to land, send it back and answer a question. It has no privilege of its own: it writes into the tracker what the human would write by hand, under the human's identity, and the lock (a separate service that checks the human's agreement in the tracker for the exact version, then merges) is unchanged. The app never talks to the release service. Rollback stays a command on the machine.

What keeps an agent, even one on the same machine, from making a gesture in the human's place:

- **Separate accesses.** The human's tokens (a Linear user token, a GitHub user token, the local tracker's signing key) live in `[app] human_credentials_dir`, mode `0700`/`0600`, owned by the app's service account, outside the project and the checkout. The agents' account has its own application token and never reads that directory; the app and the writer refuse a directory or file that is looser, a link, or one inside the project. `serve/install.sh` probes, as the agents' account, that it can read neither the credentials, the passkeys nor the access token.
- **The tracker must see the human.** Before a write the writer asks the tracker who the token is (`viewer` on Linear, `/user` on GitHub and the owner check on the local tracker) and refuses unless it is `[tracker] owner_id` and not an application or installation token. After an agreement it reads the history back and requires the human as the author.
- **A session, not just a token.** Reads accept the access token or a session. Writes accept only the session cookie (`HttpOnly`, `SameSite=Strict`, `Secure` when the connection is encrypted) plus an anti-forgery header, a same-origin check and a JSON body of bounded size; with an https `public_origin` the cookie is always `Secure` and a session made over plain http cannot write. Wrong tokens are throttled.
- **A passkey for what changes a ticket's course.** Clear to land and Send back need a WebAuthn assertion (ES256, user verification required: fingerprint, Face ID or the device PIN) on a one-time challenge bound to the session, the ticket, the exact versions and, for Send back, a hash of the text. A replayed or cloned assertion (the counter does not advance), another origin, another challenge or an unregistered key fails. An agent can reach the app by the network but cannot produce one.
- **Registration is the human's Unix account.** A passkey is registered with a one-time grant from `cleared app passkey`; the app reads the caller's UID from the kernel (`SO_PEERCRED`) on a Unix socket and answers only the human's UID, as the release broker does for rollback. With no human account configured, nobody gets a grant. The grant is redeemed once, from a signed-in session, and ten minutes at most. `cleared app passkey` reads the committed configuration from the service-owned checkout with read-only git: see [the human's commands read the service's checkout](#the-humans-commands-read-the-services-checkout).
- **The version shown is the version agreed.** The button carries the versions of the request kept in `state/validations/<ticket>.json`. The passkey challenge, the 60 second grace delay held on the server and the final write each check them again, and the writer checks the record under the same lock as `ask-validation.sh` and `merge-pr.sh`. A newer commit makes the agreement impossible, and the lock refuses a version that is not the one the human was shown anyway.
- **Everything is in the ledger.** One `app_gesture` event per attempt: time, ticket, version, device, result.

Limits: whoever holds the human's Unix account, the phone with its passkey, or the unlocked session can do what the human can. The service account running the app can read the credentials by design, so it must not be the agents' account (the app does not run the agents). With the local tracker and `[security] allow_shared_uid`, the app and the agents share an account and none of this is a boundary; `cleared status` keeps its warning. The app writes through a child process so the web server never holds the tokens, but they are in the service account's reach.

## The human's commands read the service's checkout

`cleared status`, `cleared app passkey`, `cleared rollback` and `cleared ticket` run under the human's Unix account and read the project checkout, which belongs to the service account (and `cleared` finds the project through the tool's own checkout when none is named). Git refuses a repository owned by another account ("detected dubious ownership") for a reason: its owner can put commands in `.git/config` and `.git/hooks` that git runs for whoever reads it (`core.fsmonitor` runs on `git ls-files` and `git status`, a hook on an index refresh, `gpg.program` on `git log` of a signed commit, an external diff, a pager). So Cleared's Node code never declares the checkout safe on its own: every git command it runs on a checkout goes through `checkoutReadEnv` in `lib/git-checkout.mjs`, which, for that one command and through its environment (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n`, appended after the caller's entries, so they win):

- declares `safe.directory` for the top level of that checkout only, found without running git on it (the first directory upwards that contains `.git`, so a project named by a subdirectory such as `<repo>/.cleared` works);
- sets `core.fsmonitor=false`, `core.hooksPath=/dev/null` (no hook at all, `.git/hooks` included), `core.pager=cat` and `GIT_PAGER=cat` (which also wins over `pager.<command>`), `core.editor`, `sequence.editor` and `GIT_EDITOR` to `false`, `core.askPass` and `credential.helper` empty (the empty helper resets the list), `core.sshCommand=false`, `protocol.allow=never` (no transport at all: `remote.<name>.uploadpack`, `ext::`, `core.gitProxy` and `insteadOf` rewrites cannot run anything), `diff.external` empty, `log.showSignature=false` and `gpg.program`, `gpg.ssh.program`, `gpg.x509.program` to `false`;
- sets `GIT_OPTIONAL_LOCKS=0`, so a read never writes into the checkout, and `GIT_TERMINAL_PROMPT=0`.

The commands are read-only plumbing: `ls-files --error-unmatch`, `rev-parse`, `rev-list`, `merge-base`, `symbolic-ref`, `show <rev>:<path>`, `show -s --format`, `log -1 --format`, `worktree list`, `remote get-url`, `config --list`, and `diff --name-only --no-ext-diff --no-textconv` between two commits. Never `status`, `add`, `checkout`, a patch diff, `fetch` or `push`: no human command needs them. A test plants each of these settings in a repository git treats as another user's and checks that no call site runs any of them; a static check refuses a git command in the Node code without the read environment, and a `diff` without those flags.

What this does not cover:

- **Drivers named by attributes.** `filter.<driver>.*`, `diff.<driver>.textconv` and `.command`, `merge.<driver>.driver` cannot be overridden by key, since the checkout chooses the driver names (`.gitattributes`, `.git/info/attributes`). They are left out by the choice of commands: none of the reads above applies a filter, a textconv or a merge driver.
- **Included files.** `include.path` and `includeIf` in the checkout's configuration cannot be turned off for one command. They only add settings, and the overrides above win over the included values too; a setting not listed above, read from an included file, is not neutralised.
- **Shell scripts.** The scripts do not use the read environment and declare nothing: under the human's account git refuses the service-owned checkout before reading its configuration. The one a human command reaches is the tracked-file check of `lib/common.sh` (`cleared status` asks `tracker.sh` for the waiting tickets): under the human's account git refuses it, so the waiting tickets are missing from that status (as before); the script says `cleared: git refused or could not read <project>: …` on its error output and records no untracked config. `serve/install.sh` also runs `git -C "$project"`, but under the service account, on its own checkout. Do not add the project to the human's global `safe.directory` (`git config --global --add safe.directory`): every git the human runs there, shell scripts included, would then read the service's configuration with nothing neutralised.
- **The service account.** It owns the checkout and is trusted not to plant configuration; the overrides narrow what a planted setting could make the human's account run, they do not make a hostile owner harmless. The service's own git commands on its own checkout (the fetch of `lib/release.mjs`, the revert in a scratch repository) keep their settings and run only under the service account.

When git refuses the checkout or cannot run, every command that reads the project settings under the human says `cleared: git refused or could not read <project>: <git's first line>` and stops with exit code 2, instead of reading the defaults and blaming a missing setting; nothing is recorded as an untracked config. A project path that does not exist, or that starts with `~` (Cleared does not expand it: give the absolute path), is said as such. The exit codes of the human's commands that read the settings are therefore 2 for this case, and 1 for a refused preview of `cleared rollback` (which says the reason before it asks). `release-request.mjs` (the human's `request_release` and `request_rollback`) exits 2 where it exited 69 before: 69 now only means that the release broker is not running, its socket is unsafe, or its reply cannot be read.

## Reporting a vulnerability

Use the private GitHub vulnerability report described in [SECURITY.md](../SECURITY.md). Do not post exploit details, credentials, or private project data in a public issue. The scope includes approval and merge checks, identity checks, adapters, guard bypasses, the dashboard, state and token handling, and installation scripts.

## Installing the release account boundary

**Upgrade step:** after updating Cleared to this version, configure `[security] agent_user` and run `serve/install.sh` before asking for another release or manual rollback. The broker service and its socket are required. If account separation is not yet available, `allow_shared_uid = true` explicitly restores the older behavior with the permanent status warning. A missing service makes `release-request.mjs` report that installation is needed; old direct merge and rollback commands cannot substitute for it. Restarting the broker while a release is active can interrupt that request; the queue retries transport failures up to `[merge] queue_max_attempts` (default 30) or `[merge] queue_hours`, then records `merge_refused` for the lead. The next wake reconciles health monitoring.

The installer does not create a system account. An administrator must create an unprivileged account (for example `cleared-agents`) with its own Claude Code and Codex login, set `[security] agent_user = cleared-agents` in the tracked project configuration, and set `[security] socket_path` to an absolute Unix socket path reachable from that account. Install bubblewrap at `/usr/bin/bwrap` or set `[security] bwrap_path` to its executable. Give the service account passwordless, noninteractive `sudo -u cleared-agents` for launching the harness CLIs and the installer’s UID, socket, and write probes; do not grant the reverse direction. The target account needs a PATH containing its own `.local/bin` so both CLIs can start. Do not give it GitHub merge or push credentials, the tracker owner key, or the service’s token files. Keep the Cleared checkout, the project's main checkout, `.cleared/agents.conf`, and the state tree owned by the service account. Give the agent account traversal and read access to the tool checkout and tracked project configuration without write; service home directories often default to mode `0700`, so add an explicit ACL on those paths. Give it traversal through the state path so the release client can check the state's owner, but keep the state directory and its contents unreadable and unwritable unless a selected file is needed. Give the agent account write access only to team worktrees and its CLI home. Verify both `sudo -n -u cleared-agents -- id -un` and `sudo -n -u cleared-agents -- test ! -w <Cleared state directory>` before enabling the broker.

The socket needs a service-owned, non-world-writable parent directory that the agent account can traverse. Give the socket parent execute permission to the agent account and set the socket path in the tracked configuration; do not put it directly in `/tmp`. The broker checks peer UID using Linux `SO_PEERCRED` and rejects every UID except the service and configured agent; the client checks socket ownership before connecting. The Node service uses Python 3's standard library solely to read `SO_PEERCRED` because Node's Unix socket API does not expose it. No npm dependency or network listener is added. On the Linux host used for this change, Codex 0.162.1 failed before starting the agent because bubblewrap tried to mount the Unix socket as a regular file. An unsandboxed host Codex probe reached the socket. Because the sandbox could not connect, the Codex release role uses the host runner without its filesystem sandbox when `agent_user` is configured; the operating-system account boundary still denies state writes. Bubblewrap is used around team sessions to protect shared Git metadata, but not around the acting release lead (`[lead] live = yes`, permissions `release-live`): bubblewrap sets `NoNewPrivs`, which blocks its narrow sudo bridge, so the lead runs from the service-owned main checkout instead. The wake opens its sessions there, not in the lead's lane under `[lanes] root`, and never changes that checkout (`project-update.sh` keeps it at the base). A handover session and the lead that observes (`live = no`) keep the lane and run through bubblewrap. No script closes, resets, commits in or removes the main checkout as a lane: the terminal adapters refuse it, `kill-lane.sh` refuses a lane branch checked out there, and the tidying skips it. Check both harnesses on the actual server before relying on the lock. The installer refuses a configured `agent_user` if it can write the state directory or main checkout.

The lead's existing review and communication commands also need service-owned state and tracker credentials. `lead-command.mjs` uses a second, narrow `sudo` rule to invoke `serve/lead-actions.mjs` as the service account. The wrapper accepts only review, tracker read/comment/create, team message, host status, and digest actions; it has no merge, approval-state edit, tracker move, or arbitrary command action. Configure sudoers for the agent account to run exactly `/usr/bin/node <absolute Cleared checkout>/serve/lead-actions.mjs *` as the service account without a password, with `env_reset` and without `SETENV`; do not grant the agent account general sudo to the service account. Run `serve/install.sh` again: it checks the account UID, tries to create a file in state as the agent (which must fail), scans for writable protected paths, probes the lead wrapper, proves that each configured harness answers as the agent (below), and connects to the socket as the agent.

The installer then proves that every harness the configuration can start answers under the agents' account, before it writes or starts any unit: `serve/check-harness.sh` asks each distinct `adapter:model` named by `[roles]`, `[rules]`, `[harness]` and `[review] when_same`, with their `[fallbacks]` (an alias nothing names is not asked), one small question through the adapter's `probe`, exactly as a lane starts the CLI: `sudo -n -u <agent_user>`, the bubblewrap prefix, the same environment stripping, no API key, from an empty folder, under a timeout. It makes **one small request per configured model, on the subscription**, and prints a table. A model that does not answer (not signed in as that account, unknown model, quota, timeout) stops the installation with the model and the first line of the reason; no unit is installed or started. On a host that cannot reach the providers, `CLEARED_SKIP_HARNESS_PROBE=1 serve/install.sh` skips the probe and says so in a warning; run `serve/check-harness.sh` by hand once the host is online. Without `agent_user` the probes run as the service account, as lanes do. Fake CLIs in the test suite only prove this wiring; the installer's run on the host is the proof that the real CLIs answer.
