# Security boundaries

## Release lock threat model

A ticket, web page, pull request, review, or comment can contain instructions that mislead any agent harness. An agent may then ask to publish without approval, forge or replay a validation file, substitute another PR or commit, or invoke a merge script directly. Agent output and request fields never identify a human.

The service account owns Cleared's state, validation records, ledger, release checkout, and Unix socket. Agent processes run as the distinct `[security] agent_user`; they can edit their team worktrees and call the socket, but cannot write service state, change the service executable, its configuration, or the main checkout. The kernel's peer UID identifies the caller. The service obtains human identity and the timing of approval from the configured tracker contract. It independently checks the shown PR and commit, review verdict, green CI, and active release watch immediately before merging, under a single merge lock. Every request is logged with UID, result, reason, and commit. The service account and host administrator remain trusted.

A writable validation file is not an authority: the tracker supplies the human action. A validation record only binds the request time and the shown PR and commit; it must be written by the service account when the request is posted. Because the current tracker contracts may authenticate an integration as a person, installations that cannot distinguish owner actions from agent actions must retain the existing `separate_identity` refusal.

Without `[security] agent_user`, both harnesses run with the service account's filesystem rights. By default the broker refuses release requests and manual rollback requests. Create a separate unprivileged agent account, set `[security] agent_user` to its name, give it access to team worktrees and the socket but no write access to Cleared state, then run `serve/install.sh`. To retain the older shared-account behavior, explicitly set `[security] allow_shared_uid = true` in the tracked configuration. This permits releases and manual rollback but cannot distinguish an agent from the service or human account. `cleared status` permanently reports: “release lock is not a security boundary: agents run as the service account”. Do not treat harness allow lists, prompts, or a Codex sandbox as the security boundary.

The socket is local only. Its parent directory permits the configured agent account to connect, and peer UID checks deny unrelated users. Codex needs access to this socket path; the Linux sandbox may fail to mount a socket. Use the documented host fallback under the agent UID in that case. Never expose the broker on a TCP port.

The single agent UID covers all agent roles. A prompt-injected coding session can request approval, ask for a release, or use the narrow lead-action bridge. These calls do not identify a human and cannot authorize release; the tracker contract and service-owned run ledger supply that evidence. Role prompts and command lists remain workflow guidance, not an OS boundary between agents. Keep forge merge credentials and the tracker owner's credentials outside the agent account, and enforce branch protection on the base branch.


Cleared is alpha software that can read source code, create pull requests, and, after approval, merge them. Run it on a host and repository you control. Claude Code and Codex run on that host. Configure `[security] agent_user` to run both harnesses under a separate account. For stronger isolation, run Cleared under a dedicated operating-system account without other projects' secrets.

An automatic rollback is a direct, ordinary push of a revert commit to the configured base branch after repeated health failures. It reverts only the recorded two-parent merge commit; a conflict or a moved base makes the push fail without force. Manual rollback requires `cleared rollback` from the configured human Unix account; the broker checks its peer UID. A tracker comment cannot authorize rollback. `--yes` skips only the prompt. If the merge touched configured migration paths, automatic rollback is refused and manual rollback needs `--force-with-migrations`; Cleared never undoes database schema or data migrations. Branch protection and repository credentials must be configured so the rollback identity can push a revert, or the operation fails and alerts the owner. Health commands run with the Cleared account's permissions, so configure only trusted commands.

When `auto_rollback = true`, application code can make a health probe fail and thereby cause Cleared to revert the release without another human decision. This is the intended emergency action after a previously approved merge. Keep the health endpoint and `[release]` settings under owner review; do not make the probe depend on untrusted scripts or remote responses. A different commit appearing on the base after the release prevents automatic rollback, even if the revert would apply cleanly.

## Identities and approval

The ticket owner and the agent need separate identities. The Linear adapter prefers `LINEAR_APP_CLIENT_ID` and `LINEAR_APP_CLIENT_SECRET` for an agent application, with a short-lived token kept under the state directory. `LINEAR_API_KEY` can be used to explore and open a test team, but `[merge] separate_identity = required` blocks unattended shipping when Cleared cannot distinguish the agent from the ticket owner. Store credentials in environment variables or an untracked `.env.local`; the scripts read only the values they need. The Claude adapter removes `ANTHROPIC_API_KEY` and the Codex adapter removes `OPENAI_API_KEY` so subscription sessions do not silently switch to API billing. Both model adapters remove the known tracker and GitHub token variables before starting the CLI; keep other project secrets out of that environment. Authenticate `gh`, Claude Code, and/or Codex separately. Never put credentials in `agents.conf`, a prompt, a ticket, or a pull request.

For GitHub Issues, configure a GitHub App private key so Cleared can obtain short-lived installation tokens, and use the human account for approval. Keep the key outside the repository with mode `0600`. A harness running without `agent_user` can still read that key; limit the App to the intended repositories and permissions. Local SQLite requires separate system accounts and signed human actions; see [Ticket trackers](trackers.md). A personal GitHub token or one shared system account cannot prove an approval.

Forge credentials follow the same rule. Without [`[forge]`](configuration.md#forge), pushes, pull requests and merges use the `gh` login and git credentials of the service account. With a GitHub App configured there (or, with `[forge] use_tracker_app = yes`, the GitHub Issues tracker's app, used for both), they use the app instead: its private key lives with the service account only, outside the repository, mode `0600`; Cleared mints installation tokens that last one hour, keeps the current one in the service-owned state (mode `0600`), and hands it to `gh` for one call or to git through a credential helper, never in a command line, the ledger, a log or an error message. The agents' account has no forge credential: the model adapters remove the token variables, the credential helper settings and the dispatcher's commit identity before a harness starts, and under `agent_user` it can read neither the key nor the token (`serve/install.sh` probes both as that account). Pull requests, pushes, merges and the dispatcher's commits then show as the app's bot, so GitHub's own history tells them from the human's. A configured app that cannot give a token stops forge calls instead of falling back to the ambient credential. Give the installation only the permissions listed in [the configuration reference](configuration.md#forge). The app does not replace the human's own accesses: the owner still needs their own GitHub account (and the tokens of [the app's human writes](#the-app-acts-as-the-human)) to review, approve and administer the repository. A harness running without `agent_user` can read the key like any file of the service account.

**Upgrade note:** the forge identity is opt-in. An existing installation, including one that tracks tickets in GitHub Issues with an app, keeps pushing and merging with the service account's own credentials until `[forge]` names an app or says `use_tracker_app = yes`. Before switching, grant the installation the [permissions each feature needs](configuration.md#forge) and add `app_user_id`; `cleared status` then shows `as <app login>` on the forge line.

For application and guarded paths, the broker runs `merge-pr.sh`, which checks a reviewed commit, successful checks, the owner's own ticket move to the configured go state, and the exact version previously shown. A change touching only configured `[merge] tooling_paths` skips the ticket approval check, but still needs review and green checks. Keep that list narrow and protect the base branch in GitHub; a person with direct merge rights can bypass Cleared. The script serializes merges under a lock and rechecks before shipping. When code or a conflict resolution changes the approved version, ask again. A clean merge of the base that adds no team code can keep approval.

## Private-term guard

The guard scans text and diffs sent to an external ticket tracker or GitHub, including comments, pull requests, and commits, when they pass through Cleared scripts, regardless of which harness authored them. It does not filter instructions sent to either model. Direct CLI or network calls from a model bypass this scan; protect forge and tracker credentials outside model command access and use branch protection. It compares normalized words against SHA-256 fingerprints of project-specific private terms. `[guard] salt` must be committed in the **project's** `.cleared/agents.conf` alongside the configured fingerprint lists; installation never writes a salt. Lists include a short identifier derived from that salt. When lists are configured, a missing or mismatched salt makes the guard refuse all text until the correct salt is committed or the lists are rebuilt. Lists without an identifier are also refused. Fingerprint lists named by `[guard] terms` and `allowed` live in the project and are read from its remote base branch, not from the working team's editable files. If both list keys are omitted or set to `none`, private-term matching is disabled and one ledger event records it; generic secret checks still run. The guard also checks common secret and sensitive-data patterns and rejects text it cannot read safely.

To build a list, first commit a random `[guard] salt` and set `[guard] terms = scripts/private-terms.json` in the project config. Keep the plain-text input outside the project checkout. From the project checkout, run `CLEARED_REPO=$PWD node ../cleared/lib/guard/private-terms.mjs hash < /path/outside/project/private-terms.txt > scripts/private-terms.json`, replacing `../cleared` with your Cleared checkout path. The command writes JSON with `salt_id` and hashes. Commit and push the JSON file before enabling the list. Set `ORCH_GUARD_REF=HEAD` for this command only if the committed config has not reached `origin/main` yet; the running guard reads the remote ref. Never commit the plain-text input.

GitHub capture publishing runs OCR and the text guard before pushing image bytes to a dedicated branch. OCR can miss visual secrets; only use demo-data captures that a person inspected. The capture branch retains images in Git history.

A fingerprint list is a screening rule, not encryption or a guarantee against disclosure. It cannot catch terms that were never listed, encoded or transformed data, or every form of secret. A model or process with unrestricted network or file access can bypass text scanning; isolate it with host permissions, containers, and repository rules appropriate to your project. Do not copy real private terms into this tool repository.

## Permissions and host access

`[permissions.<role>]` maps role intent to each provider CLI. Claude receives command prefixes; Codex receives filesystem and network sandbox settings. Neither offers exactly the same controls as the other. Codex hides common credential stores from sandboxed commands, but both harnesses may read other files available to the Cleared account. Development roles need network access for TCP test databases, so they can also contact external destinations unless the host enforces a separate network policy. The release role calls the broker over a Unix socket. With `agent_user`, filesystem ownership prevents both harnesses from writing approval state. Cleared mounts the shared Git control directory and each team's `.git` entry read-only around either harness; the dispatcher commits changes after a session. See the [role table](adapters.md#existing-adapters). The project lead and reviewer should be read-only; development roles may edit their own worktrees. `when-free.sh` gates commands that compete for host resources, such as screen tests. This is scheduling, not isolation. Dependencies from the base lock file are installed by the dispatcher with `npm ci --ignore-scripts`; a team's new dependency waits for CI after its pull request. Review CI and deployment workflows as carefully as code: `[merge] guarded_paths` should include them and the Cleared lock scripts.

The optional dashboard contains ticket titles and host status. `serve/install.sh` binds it to the host's Tailscale address and verifies that only the page is served. Configure network access separately; `serve/check.sh` can also probe from an existing container when `CLEARED_CHECK_CONTAINER` is set. The [Cleared app](app.md) is held to the same checks on its own port and also needs an access token: it shows no money amount, and its token file is private and outside the project. Its writes are described next. No container is required for the normal check. State and tokens are kept outside the repository under `~/.local/state/cleared/<project>/`; limit filesystem access to that directory.

## The app acts as the human

The [Cleared app](app.md) can clear a ticket to land, send it back and answer a question. It has no privilege of its own: it writes into the tracker what the human would write by hand, under the human's identity, and the lock (a separate service that checks the human's agreement in the tracker for the exact version, then merges) is unchanged. The app never talks to the release service. Rollback stays a command on the machine.

What keeps an agent, even one on the same machine, from making a gesture in the human's place:

- **Separate accesses.** The human's tokens (a Linear user token, a GitHub user token, the local tracker's signing key) live in `[app] human_credentials_dir`, mode `0700`/`0600`, owned by the app's service account, outside the project and the checkout. The agents' account has its own application token and never reads that directory; the app and the writer refuse a directory or file that is looser, a link, or one inside the project. `serve/install.sh` probes, as the agents' account, that it can read neither the credentials, the passkeys nor the access token.
- **The tracker must see the human.** Before a write the writer asks the tracker who the token is (`viewer` on Linear, `/user` on GitHub and the owner check on the local tracker) and refuses unless it is `[tracker] owner_id` and not an application or installation token. After an agreement it reads the history back and requires the human as the author.
- **A session, not just a token.** Reads accept the access token or a session. Writes accept only the session cookie (`HttpOnly`, `SameSite=Strict`, `Secure` when the connection is encrypted) plus an anti-forgery header, a same-origin check and a JSON body of bounded size; with an https `public_origin` the cookie is always `Secure` and a session made over plain http cannot write. Wrong tokens are throttled.
- **A passkey for what changes a ticket's course.** Clear to land and Send back need a WebAuthn assertion (ES256, user verification required: fingerprint, Face ID or the device PIN) on a one-time challenge bound to the session, the ticket, the exact versions and, for Send back, a hash of the text. A replayed or cloned assertion (the counter does not advance), another origin, another challenge or an unregistered key fails. An agent can reach the app by the network but cannot produce one.
- **Registration is the human's Unix account.** A passkey is registered with a one-time grant from `cleared app passkey`; the app reads the caller's UID from the kernel (`SO_PEERCRED`) on a Unix socket and answers only the human's UID, as the release broker does for rollback. With no human account configured, nobody gets a grant. The grant is redeemed once, from a signed-in session, and ten minutes at most.
- **The version shown is the version agreed.** The button carries the versions of the request kept in `state/validations/<ticket>.json`. The passkey challenge, the 60 second grace delay held on the server and the final write each check them again, and the writer checks the record under the same lock as `ask-validation.sh` and `merge-pr.sh`. A newer commit makes the agreement impossible, and the lock refuses a version that is not the one the human was shown anyway.
- **Everything is in the ledger.** One `app_gesture` event per attempt: time, ticket, version, device, result.

Limits: whoever holds the human's Unix account, the phone with its passkey, or the unlocked session can do what the human can. The service account running the app can read the credentials by design, so it must not be the agents' account (the app does not run the agents). With the local tracker and `[security] allow_shared_uid`, the app and the agents share an account and none of this is a boundary; `cleared status` keeps its warning. The app writes through a child process so the web server never holds the tokens, but they are in the service account's reach.

## Reporting a vulnerability

Use the private GitHub vulnerability report described in [SECURITY.md](../SECURITY.md). Do not post exploit details, credentials, or private project data in a public issue. The scope includes approval and merge checks, identity checks, adapters, guard bypasses, the dashboard, state and token handling, and installation scripts.

## Installing the release account boundary

**Upgrade step:** after updating Cleared to this version, configure `[security] agent_user` and run `serve/install.sh` before asking for another release or manual rollback. The broker service and its socket are required. If account separation is not yet available, `allow_shared_uid = true` explicitly restores the older behavior with the permanent status warning. A missing service makes `release-request.mjs` report that installation is needed; old direct merge and rollback commands cannot substitute for it. Restarting the broker while a release is active can interrupt that request; the queue retries transport failures up to `[merge] queue_max_attempts` (default 30) or `[merge] queue_hours`, then records `merge_refused` for the lead. The next wake reconciles health monitoring.

The installer does not create a system account. An administrator must create an unprivileged account (for example `cleared-agents`) with its own Claude Code and Codex login, set `[security] agent_user = cleared-agents` in the tracked project configuration, and set `[security] socket_path` to an absolute Unix socket path reachable from that account. Install bubblewrap at `/usr/bin/bwrap` or set `[security] bwrap_path` to its executable. Give the service account passwordless, noninteractive `sudo -u cleared-agents` for launching the harness CLIs and the installer’s UID, socket, and write probes; do not grant the reverse direction. The target account needs a PATH containing its own `.local/bin` so both CLIs can start. Do not give it GitHub merge or push credentials, the tracker owner key, or the service’s token files. Keep the Cleared checkout, the project's main checkout, `.cleared/agents.conf`, and the state tree owned by the service account. Give the agent account traversal and read access to the tool checkout and tracked project configuration without write; service home directories often default to mode `0700`, so add an explicit ACL on those paths. Give it traversal through the state path so the release client can check the state's owner, but keep the state directory and its contents unreadable and unwritable unless a selected file is needed. Give the agent account write access only to team worktrees and its CLI home. Verify both `sudo -n -u cleared-agents -- id -un` and `sudo -n -u cleared-agents -- test ! -w <Cleared state directory>` before enabling the broker.

The socket needs a service-owned, non-world-writable parent directory that the agent account can traverse. Give the socket parent execute permission to the agent account and set the socket path in the tracked configuration; do not put it directly in `/tmp`. The broker checks peer UID using Linux `SO_PEERCRED` and rejects every UID except the service and configured agent; the client checks socket ownership before connecting. The Node service uses Python 3's standard library solely to read `SO_PEERCRED` because Node's Unix socket API does not expose it. No npm dependency or network listener is added. On the Linux host used for this change, Codex 0.162.1 failed before starting the agent because bubblewrap tried to mount the Unix socket as a regular file. An unsandboxed host Codex probe reached the socket. Because the sandbox could not connect, the Codex release role uses the host runner without its filesystem sandbox when `agent_user` is configured; the operating-system account boundary still denies state writes. Bubblewrap is used around team sessions to protect shared Git metadata, but not around the release lead: bubblewrap sets `NoNewPrivs`, which blocks its narrow sudo bridge, and the lead runs from the service-owned main checkout. Check both harnesses on the actual server before relying on the lock. The installer refuses a configured `agent_user` if it can write the state directory or main checkout.

The agent asks for approval through `release-request.mjs request_release TICKET PR --ask` and later calls `release-request.mjs request_release TICKET PR` with the announcement on standard input. The broker writes the request record and checks the tracker action; the agent never writes a validation record. Only the configured human Unix account can request manual rollback through `cleared rollback`; automatic rollback still follows the health gate. Set `[security] human_user` for remote trackers; with the local tracker, `[tracker] owner_id` is the default Unix account. In explicit `allow_shared_uid` mode without a named human account, the service UID is accepted for manual rollback and the permanent warning applies. The human account needs socket traversal and read access to the ledger for the CLI preview. No agent or tracker comment can authorize rollback. Socket access alone does not authorize a release or rollback.

The lead's existing review and communication commands also need service-owned state and tracker credentials. `lead-command.mjs` uses a second, narrow `sudo` rule to invoke `serve/lead-actions.mjs` as the service account. The wrapper accepts only review, tracker read/comment/create, team message, host status, and digest actions; it has no merge, approval-state edit, tracker move, or arbitrary command action. Configure sudoers for the agent account to run exactly `/usr/bin/node <absolute Cleared checkout>/serve/lead-actions.mjs *` as the service account without a password, with `env_reset` and without `SETENV`; do not grant the agent account general sudo to the service account. The wrapper rebuilds its environment from service-owned project and state pointers, and the installer probes that `NODE_OPTIONS` is removed before Node starts as the service account. A project-owned release prompt that still names the old direct scripts must be updated to the broker and lead client commands before enabling the split account.

For example, an administrator can create the account with `sudo useradd --create-home --shell /bin/bash cleared-agents`, and create a service-owned socket directory with `sudo install -d -o cleared-service -g cleared-service -m 0711 /srv/cleared-run`. Set `socket_path = /srv/cleared-run/release.sock` in the tracked config. Replace `cleared-service` with the actual account running the user systemd units. A sudoers file edited with `visudo` can grant `cleared-service ALL=(cleared-agents) NOPASSWD: ALL` and `cleared-agents ALL=(cleared-service) NOPASSWD: /usr/bin/node /absolute/path/to/cleared/serve/lead-actions.mjs *`. Keep `env_reset` enabled. Give `cleared-agents` read and traversal ACLs on the Cleared checkout and main project, and write ACLs on team worktrees only. Authenticate Claude and Codex in the new account. Run `serve/install.sh` again: it checks the account UID, tries to create a file in state as the agent (which must fail), scans for writable protected paths, probes the lead wrapper, and connects to the socket as the agent.
