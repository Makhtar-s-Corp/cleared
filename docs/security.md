# Security boundaries

Cleared is alpha software that can read source code, create pull requests, and, after approval, merge them. Run it on a host and repository you control. Claude Code and Codex run on that host by default under the same role configuration. Either harness can read everything that the account running Cleared can read. For stronger isolation, run Cleared under a dedicated operating-system account without other projects' secrets.

An automatic rollback is a direct, ordinary push of a revert commit to the configured base branch after repeated health failures. It reverts only the recorded two-parent merge commit; a conflict or a moved base makes the push fail without force. Manual rollback requires the configured human owner's verified tracker or local account identity. `--yes` skips only the prompt. If the merge touched configured migration paths, automatic rollback is refused and manual rollback needs `--force-with-migrations`; Cleared never undoes database schema or data migrations. Branch protection and repository credentials must be configured so the rollback identity can push a revert, or the operation fails and alerts the owner. Health commands run with the Cleared account's permissions, so configure only trusted commands.

When `auto_rollback = true`, application code can make a health probe fail and thereby cause Cleared to revert the release without another human decision. This is the intended emergency action after a previously approved merge. Keep the health endpoint and `[release]` settings under owner review; do not make the probe depend on untrusted scripts or remote responses. A different commit appearing on the base after the release prevents automatic rollback, even if the revert would apply cleanly.

## Identities and approval

The ticket owner and the agent need separate identities. The Linear adapter prefers `LINEAR_APP_CLIENT_ID` and `LINEAR_APP_CLIENT_SECRET` for an agent application, with a short-lived token kept under the state directory. `LINEAR_API_KEY` can be used to explore and open a test team, but `[merge] separate_identity = required` blocks unattended shipping when Cleared cannot distinguish the agent from the ticket owner. Store credentials in environment variables or an untracked `.env.local`; the scripts read only the values they need. The Claude adapter removes `ANTHROPIC_API_KEY` and the Codex adapter removes `OPENAI_API_KEY` so subscription sessions do not silently switch to API billing. Both model adapters remove the known tracker and GitHub token variables before starting the CLI; keep other project secrets out of that environment. Authenticate `gh`, Claude Code, and/or Codex separately. Never put credentials in `agents.conf`, a prompt, a ticket, or a pull request.

For GitHub Issues, configure a GitHub App private key so Cleared can obtain short-lived installation tokens, and use the human account for approval. Keep the key outside the repository with mode `0600`. A harness running as the Cleared account can still read that key; limit the App to the intended repositories and permissions. Local SQLite requires separate system accounts and signed human actions; see [Ticket trackers](trackers.md). A personal GitHub token or one shared system account cannot prove an approval.

For application and guarded paths, `merge-pr.sh` checks a reviewed commit, successful checks, the owner's own ticket move to the configured go state, and the exact version previously shown. A change touching only configured `[merge] tooling_paths` skips the ticket approval check, but still needs review and green checks. Keep that list narrow and protect the base branch in GitHub; a person with direct merge rights can bypass Cleared. The script serializes merges under a lock and rechecks before shipping. When code or a conflict resolution changes the approved version, ask again. A clean merge of the base that adds no team code can keep approval.

## Private-term guard

The guard scans text and diffs sent to an external ticket tracker or GitHub, including comments, pull requests, and commits, when they pass through Cleared scripts, regardless of which harness authored them. It does not filter instructions sent to either model. Direct CLI or network calls from a model bypass this scan; protect forge and tracker credentials outside model command access and use branch protection. It compares normalized words against SHA-256 fingerprints of project-specific private terms. `[guard] salt` must be committed in the **project's** `.cleared/agents.conf` alongside the configured fingerprint lists; installation never writes a salt. Lists include a short identifier derived from that salt. When lists are configured, a missing or mismatched salt makes the guard refuse all text until the correct salt is committed or the lists are rebuilt. Lists without an identifier are also refused. Fingerprint lists named by `[guard] terms` and `allowed` live in the project and are read from its remote base branch, not from the working team's editable files. If both list keys are omitted or set to `none`, private-term matching is disabled and one ledger event records it; generic secret checks still run. The guard also checks common secret and sensitive-data patterns and rejects text it cannot read safely.

To build a list, first commit a random `[guard] salt` and set `[guard] terms = scripts/private-terms.json` in the project config. Keep the plain-text input outside the project checkout. From the project checkout, run `CLEARED_REPO=$PWD node ../cleared/lib/guard/private-terms.mjs hash < /path/outside/project/private-terms.txt > scripts/private-terms.json`, replacing `../cleared` with your Cleared checkout path. The command writes JSON with `salt_id` and hashes. Commit and push the JSON file before enabling the list. Set `ORCH_GUARD_REF=HEAD` for this command only if the committed config has not reached `origin/main` yet; the running guard reads the remote ref. Never commit the plain-text input.

GitHub capture publishing runs OCR and the text guard before pushing image bytes to a dedicated branch. OCR can miss visual secrets; only use demo-data captures that a person inspected. The capture branch retains images in Git history.

A fingerprint list is a screening rule, not encryption or a guarantee against disclosure. It cannot catch terms that were never listed, encoded or transformed data, or every form of secret. A model or process with unrestricted network or file access can bypass text scanning; isolate it with host permissions, containers, and repository rules appropriate to your project. Do not copy real private terms into this tool repository.

## Permissions and host access

`[permissions.<role>]` maps role intent to each provider CLI. Claude receives command prefixes; Codex receives filesystem and network sandbox settings. Neither offers exactly the same controls as the other. Codex hides common credential stores from sandboxed commands, but both harnesses may read other files available to the Cleared account. Development roles need network access for TCP test databases, so they can also contact external destinations unless the host enforces a separate network policy. A `release-live` host Codex run refuses to start when trusted scripts need write access to approval state; without a command allowlist the model could otherwise change that state directly. Codex commits need write access to the shared Git loose-object store and branch namespace; Cleared protects Git control files and existing sibling refs, but this is not a data-loss boundary against a hostile harness. See the [role table](adapters.md#existing-adapters). The project lead and reviewer should be read-only; development roles may edit their own worktrees. `when-free.sh` gates commands that compete for host resources, such as screen tests. This is scheduling, not isolation. Dependencies from the base lock file are installed by the dispatcher with `npm ci --ignore-scripts`; a team's new dependency waits for CI after its pull request. Review CI and deployment workflows as carefully as code: `[merge] guarded_paths` should include them and the Cleared lock scripts.

The optional dashboard contains ticket titles and host status. `serve/install.sh` binds it to the host's Tailscale address and verifies that only the page is served. Configure network access separately; `serve/check.sh` can also probe from an existing container when `CLEARED_CHECK_CONTAINER` is set. No container is required for the normal check. State and tokens are kept outside the repository under `~/.local/state/cleared/<project>/`; limit filesystem access to that directory.

## Reporting a vulnerability

Use the private GitHub vulnerability report described in [SECURITY.md](../SECURITY.md). Do not post exploit details, credentials, or private project data in a public issue. The scope includes approval and merge checks, identity checks, adapters, guard bypasses, the dashboard, state and token handling, and installation scripts.
