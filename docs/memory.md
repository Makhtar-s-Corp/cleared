# Project memory

Cleared starts each agent session fresh. When `[memory] enabled = true`, the dispatcher prepares a bounded briefing before the role prompt. The text is labelled as reference data, with its source, and tells the model to ignore and report any passage that reads like an instruction. This marking reduces prompt injection risk; it cannot guarantee that a model will always ignore hostile text.

The local adapter indexes the project's decision files, glossary, project overview, and role lessons in place. It does not write them. Use one decision per Markdown file and `## Term` headings for individual glossary entries. It stores handovers and machine events in SQLite beside the ledger. Node's SQLite FTS5 index is used when available; a simple scan provides the same basic content search when FTS5 is missing. File hashes avoid unnecessary reindexing. No model extraction, embeddings, npm package, or external memory service is involved.

An entry has an ID, type, scope, short Markdown content, source identity, location and time, status, links, superseded entry, and last briefing use. All new entries start as proposals. Find IDs with `node lib/ledger.ts sql 'select id, type, scope, source_where, status from memory_entries'` after a search or briefing has indexed the files. Only a verified human owner action can approve an entry. The owner can run `node lib/memory/cli.ts approve ENTRY_ID` under their own local tracker account, or post exactly `Approve memory ENTRY_ID` on a ticket and run `node lib/memory/cli.ts approve ENTRY_ID TICKET_ID COMMENT_ID`. This uses the tracker adapter's verified comment author, including with remote trackers. A decision file needs both committed content and explicit approval of its indexed entry before it appears among approved decisions. Editing it resets that approval. A `status: approved` line in Markdown does not grant approval. The host account that runs Cleared can still edit everything it can read or write; use a dedicated account when isolation matters.

The briefing includes the committed project overview, committed role lessons, the newest handover for the ticket in full, up to five approved decisions matching the ticket text, and committed glossary entries matching the ticket text. Project, lesson, and glossary files appear as reference data with `proposed` status; a commit does not approve them. Uncommitted file edits remain searchable but are not briefed. Each block has a source label and a data boundary. If a block does not fit the byte budget, Cleared tries the next block and records the omitted ID; a handover is never cut halfway. The ledger records the IDs actually included.

Every enabled lane is asked to write `HANDOVER.md` with the five required headings at its worktree root. Cleared excludes it from normal `git add -A`, stores it after the harness exits, then removes the file. This also runs when a harness refuses or stops at a limit. A missing or malformed file is recorded in the ledger, and the next briefing for that ticket says so. A hard power loss can leave a file in the worktree; inspect it before discarding the worktree.

The project lead's `prompts/handover.md` is different: it guides a new lead after a lead transition. It is not a lane session handover and is not added as a ticket handover entry.

## In Cleared v2: three levels

Cleared v2 (`v2/`) runs the same `lib/memory` for every session, in a child process, and writes the briefing as `CLAUDE.md` at the root of the ticket's checkout (`v2/src/workspace/briefing.ts`). Since milestone 2, a workspace of several services has three levels of memory, each one `lib/memory` with its own checkout and its own state folder:

- **The workspace.** Milestone 1's memory, where it already is: the ledger the service already uses, read on the workspace's checkout (its first service's). It holds each ticket's handovers, the approved decisions and the `handover_missing` events.
- **A service.** `<state>/services/<name>/memory`, read on that service's checkout: its `docs/project.md`, its glossary, its decisions and its role lessons, as its own `.cleared/agents.conf` names them. The first service has no level of its own, since its checkout is the workspace's.
- **A contract.** `<state>/contracts/<name>/memory`, named by the service that provides the contract, read on the provider's checkout. Its files sit beside the contract file, by its name without the extension: for `contract/openapi.yaml`, the page `contract/openapi.md`, the glossary `contract/openapi.glossary.md`, the decisions `contract/openapi.decisions/` and the role lessons `contract/openapi.lessons/<role>.md`. The provider's own page is not the contract's.

`<state>` is the folder of the workspace's memory: `CLEARED_STATE_DIR`, else `ORCH_STATE_DIR`, else the folder of `ORCH_LEDGER`. Each level is given its own `CLEARED_STATE_DIR`, `ORCH_STATE_DIR`, `CLEARED_LEDGER` and `ORCH_LEDGER`, so no level writes another's ledger.

A session on a service is briefed with the workspace's memory, then its service's, then the memory of each contract it touches: its service's own, those of the services it consumes, then those of the ticket's other services. The levels share one byte budget: the one the workspace's settings give the role (`[memory] budget_<role>`, else `budget`). Each level gets what the levels before it left, counted in the bytes of `lib/memory`'s text, its reference line once. A level with no room left, or whose checkout is not on the server, is named in the briefing and not read; the session still starts. The author's session fetches the workspace's checkout and the providers' before it is briefed. A one-service workspace is briefed exactly as in milestone 1.

A handover may end with three optional sections: `## Lessons for the workspace`, `## Lessons for the service` and `## Lessons for the contract`. A heading counts at the start of a line, outside a code block, and the section runs to the next level-two heading. After the handover is stored for the ticket, each section is written as a lesson of the author's role in its level, with the session as its source, as a **proposal**. A proposal is never briefed: v2's knowledge items (milestone 2, lane 24) take it to the owner. The service is the one whose checkout the session worked in; the first service's lessons go to the workspace's memory, since its checkout is the workspace's. The contract is the service's own, else the first one the service consumes. A level the session does not have files into the workspace's memory, so every lesson is in a memory some briefing reads. A lesson that cannot be filed is logged, and the handover is stored all the same. The briefing of a workspace of several services tells the author where each section goes.

The project lead's memory is the workspace's level. After it, the lead's briefing lists the first line of each other service's page, read in that service's level: at most 160 bytes per line and 2000 bytes in all, taken from the lead's 12 000-byte budget.
