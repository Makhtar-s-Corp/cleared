# Project memory

Cleared starts each agent session fresh. When `[memory] enabled = true`, the dispatcher prepares a bounded briefing before the role prompt. The text is labelled as reference data, with its source, and tells the model to ignore and report any passage that reads like an instruction. This marking reduces prompt injection risk; it cannot guarantee that a model will always ignore hostile text.

The local adapter indexes the project's decision files, glossary, project overview, and role lessons in place. It does not write them. Use one decision per Markdown file and `## Term` headings for individual glossary entries. It stores handovers and machine events in SQLite beside the ledger. Node's SQLite FTS5 index is used when available; a simple scan provides the same basic content search when FTS5 is missing. File hashes avoid unnecessary reindexing. No model extraction, embeddings, npm package, or external memory service is involved.

An entry has an ID, type, scope, short Markdown content, source identity, location and time, status, links, superseded entry, and last briefing use. All new entries start as proposals. Find IDs with `node lib/ledger.mjs sql 'select id, type, scope, source_where, status from memory_entries'` after a search or briefing has indexed the files. Only a verified human owner action can approve an entry. The owner can run `node lib/memory/cli.mjs approve ENTRY_ID` under their own local tracker account, or post exactly `Approve memory ENTRY_ID` on a ticket and run `node lib/memory/cli.mjs approve ENTRY_ID TICKET_ID COMMENT_ID`. This uses the tracker adapter's verified comment author, including with remote trackers. A decision file needs both committed content and explicit approval of its indexed entry before it appears among approved decisions. Editing it resets that approval. A `status: approved` line in Markdown does not grant approval. The host account that runs Cleared can still edit everything it can read or write; use a dedicated account when isolation matters.

The briefing includes the committed project overview, committed role lessons, the newest handover for the ticket in full, up to five approved decisions matching the ticket text, and committed glossary entries matching the ticket text. Project, lesson, and glossary files appear as reference data with `proposed` status; a commit does not approve them. Uncommitted file edits remain searchable but are not briefed. Each block has a source label and a data boundary. If a block does not fit the byte budget, Cleared tries the next block and records the omitted ID; a handover is never cut halfway. The ledger records the IDs actually included.

Every enabled lane is asked to write `HANDOVER.md` with the five required headings at its worktree root. Cleared excludes it from normal `git add -A`, stores it after the harness exits, then removes the file. This also runs when a harness refuses or stops at a limit. A missing or malformed file is recorded in the ledger, and the next briefing for that ticket says so. A hard power loss can leave a file in the worktree; inspect it before discarding the worktree.

The project lead's `prompts/handover.md` is different: it guides a new lead after a lead transition. It is not a lane session handover and is not added as a ticket handover entry.
