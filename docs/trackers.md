# Ticket trackers

Cleared uses `[tracker] adapter = linear | github | local`. The ticket interface is defined in [`lib/tracker/contract.mjs`](../lib/tracker/contract.mjs): `listTickets`, `getTicket`, `createTicket`, `moveTicket`, `history`, `comments`, `comment`, `editComment`, `whoAmI`, and `changesSince`. `tracker.sh` is the shell entry point for the existing orchestration scripts. Every adapter returns ticket title, body, labels, project, status, and timestamps; comments and status history carry an actor and a time. An unknown actor never counts as a human approval.

The project names its own `todo_state`, `progress_state`, `review_state`, `validate_state`, `go_state`, and `done_state`. Scripts may move tickets to progress, review, validation, or done, but never to the approval state. Before shipping, Cleared checks that the configured human moved the ticket to `go_state` after the approval request and that the pull request still matches the version shown. A comment or a status change by an agent or another integration cannot stand in for that move.

## Linear

Set `adapter = linear`, `team`, and the six state names. Set `create_project` and `create_label` for ticket creation through the contract. Use `LINEAR_APP_CLIENT_ID` and `LINEAR_APP_CLIENT_SECRET` for the agent identity and set `owner_id` to the human's Linear user ID. A personal `LINEAR_API_KEY` is useful for exploration but is a shared identity; the default `[merge] separate_identity = required` refuses unattended shipping with it. Linear supports native image uploads. Existing ticket formatting, rate limiting, and the status-history approval check remain in the Linear adapter.

## GitHub Issues

Set `adapter = github`, `repository = owner/repo`, `owner_id = <human login>`, `app_login = <GitHub App bot login>`, and the six state names. Configure the numeric GitHub App `app_id` and `installation_id`, plus an absolute `app_private_key_file` path. Keep that RSA private key outside the repository, owned by the Cleared account with mode `0600`. The app needs Issues write and Contents write, plus Projects write if it uses a Project v2 status field. Cleared obtains an installation token at each script invocation and re-requests one if less than five minutes remain before expiry during that invocation. [GitHub installation tokens normally expire after one hour](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app). `GH_TOKEN` alone is not accepted for the tracker, so an old or personal token cannot silently become the agent identity. The human uses their own GitHub account in the Issues interface. Pull requests, pushes and merges keep the service account's own `gh` and git credentials unless [`[forge]`](configuration.md#forge) names an app. To use this same app for them, set `[forge] use_tracker_app = yes` after granting it the forge permissions listed there (Pull requests write among them); `[forge] app_user_id` then gives the dispatcher's commits the bot's identity. Upgrading Cleared does not change an existing installation without that line.

Without `project_v2_id`, create one `status:<name>` label for every configured state. Every issue must have exactly one active status label. Cleared removes the previous status before adding the next without replacing unrelated labels; it tries to restore the old status if the add fails. An API failure can still leave no clear status, which Cleared reports and skips until repaired. The label timeline supplies author and timestamp. If `project_v2_id` names a Project v2 node, Cleared uses its single-select `Status` field and reads field-change events with their actors from the issue timeline. Automated changes do not count as human actions. The status names must match the Project options.

GitHub's issue-comment API has no native image attachment. Cleared publishes captures to the `cleared-captures` branch of the configured repository and links a pinned commit in the comment. `[tracker] capture_roots` limits which PNG and JPEG files can be published. Upload requires Tesseract OCR; Cleared checks the recognized text with the project guard and refuses an image it cannot read or whose recognized text is empty. OCR can miss visual secrets, so use demonstration data and inspect captures before requesting approval. GitHub stores the image in repository history; deleting the issue comment does not remove it. This needs Contents write access and is less convenient than Linear's native upload. Set `capture_branch` and `capture_base` if the defaults are unsuitable.

GitHub removes the previous status label before adding the next, then restores the old one if the add fails. This can briefly leave the issue without a status. If an issue has no status or multiple status labels, the adapter reports and skips that ticket while continuing with others. A ticket classified later and its earlier comments are handed to the next wake. Issues outside the configured Project are skipped. Project v2 requires a configured project and additional permission. The initial adapter has no webhook subscription: label mode polls issues updated since the previous wake, while Project v2 mode pages through project items and fetches issues whose item or issue changed. Project v2 polling is slower than label mode on large projects. An edited human comment is treated as untrusted because the issue-comment API does not identify the editor. GitHub remains the only forge used for pull requests.

## Local SQLite

Set `adapter = local` and the six state names. Tickets, comments, history, and image bytes live in Cleared's `ledger.db`. Configure one absolute shared state path and export `CLEARED_STATE_DIR` to that path for both the Cleared service and the human CLI; the CLI refuses to run without it so separate accounts cannot silently create separate databases. From the project checkout, use `CLEARED_REPO=$PWD CLEARED_STATE_DIR=/srv/cleared-state/sample ../cleared/cleared ticket new '<title>' [body-file]`, then `ticket show LOCAL-1`, `ticket comment LOCAL-1 body.md`, and `ticket move LOCAL-1 '<status>'` with the same environment and under the appropriate system account. No ticket operation needs a network service. The future Cleared app can use the same adapter.

Local approval needs two separate system accounts. Set `agents_uid` to the UID running Cleared and `owner_id` to the human account name. Set `human_private_key` to an absolute path readable only by that human account, and commit `human_public_key` as base64-encoded PEM in the project config. Generate an Ed25519 key pair with `openssl genpkey -algorithm Ed25519 -out ~/.config/cleared/tracker.key` and `openssl pkey -in ~/.config/cleared/tracker.key -pubout | base64 -w0`. Set mode `0600` on the private key; the CLI checks its owner and mode before signing. Give both accounts access to the state directory and SQLite file through a dedicated group, while keeping the private key outside that group. A human ticket creation signs its title, body, labels, and project. A human status change or comment is also signed; an approval signature binds the request timestamp and all presented pull-request heads. Unsigned, altered, or replayed approval rows cannot authorize a different request. An agent running under the same UID as the human cannot create a verifiable approval.

Local mode has no remote ticket notifications, browser UI, or shareable ticket URLs. The CLI is the user interface, and the daemon discovers changes by reading SQLite on each wake. The project still needs GitHub for pull requests and merges. SQLite and project access must be backed up together. The signing key proves attribution of a status transition; it does not protect the database against deletion by an account with write access.

## The human's accesses for the app

The [app](app.md) writes as the human, with accesses of their own, distinct from the agents'. Put them in `[app] human_credentials_dir` (default `~/.config/cleared/human`, mode `0700`, owned by the account that runs the app, outside the project, unreadable by the agents' account) as `credentials.json`, mode `0600`:

```json
{ "linear": "…", "github": "…" }
```

One user token per adapter, keyed by the adapter's name; only the adapter in use is needed (the local tracker needs none, it signs with `human-signing.key`). The tracker must see the access as `[tracker] owner_id`; the writer checks it before every write and refuses an application or installation token.

- **Linear.** An OAuth access token in *user* mode (not the application of the agents): create a Linear OAuth application, authorise it once as yourself with the `read` and `write` scopes (authorisation-code flow, no `actor=app`), and keep the access token (and refresh it when it expires, replacing the file). `owner_id` is your Linear user id. A personal API key also works for the writer but Linear cannot then tell a program acting under your account from you, so prefer the OAuth token.
- **GitHub.** A fine-grained personal access token of the owner account (`owner_id`), limited to the repository, with *Issues: read and write* (and *Projects: read and write* when `project_v2_id` is set), kept under `github`. It must not be the GitHub App's installation token: the writer reads `/user` and refuses a bot.
- **Local SQLite.** The signing key that goes with `human_public_key`: copy the human's Ed25519 private key to `human-signing.key` in the credentials directory, owned by the app's account, mode `0600` (the human's own copy stays in their account). The app signs its writes with it, so the tracker's history shows them as the human's.

A different API address (GitHub Enterprise, a test double) is set in the service's environment (`CLEARED_APP_GITHUB_API`, `CLEARED_APP_LINEAR_API`), never in the project's settings.
