## 2026-10-28: a session survives the crash of its container, recreated through the adapter's resume, at most three times (the author's choices, lane `v2-j6-session-survives`, B5.1a, B5.4a, P25, P264, issue #453)

**The need.** Milestone 6, wave 2, issue #453 (linked to #436, done by pull request 454). A session's container that stops before the session is done must be detected by the service, recreated from the same environment on the same checkout, and the session resumed through the adapter's resume; after a fixed number of failures the session stops with a readable reason, with no loop. Acceptance: a test kills a running session's container (`docker kill`, label-filtered, on a container the test made) and the session resumes with no intervention; the thread stays continuous with a "container recreated" event in French and English; the checkout's uncommitted work is kept; the session's cost adds both processes, with no double counting; after three failures the session stops with a visible reason and its Docker objects are cleaned; a session taken over (P25) is never restarted automatically; Claude Code works, and Codex is documented if it cannot resume. Out of scope: a restart of the service itself (#58), moving the agent loop out of the harness, the setup check's resume (#436). The brief names a milestone 6 plan's section for this lane; no milestone 6 plan is in the repository, so the lane follows the issue, the brief and the conventions of [milestone-5-plan.md](milestone-5-plan.md) section 3.1, as lane `v2-j6-workspace-reload` did.

**The branch.** Renamed to `v2-j6-session-survives`, from `origin/v2` at `584d3ebe` (pull request 456).

**What was found.** The pieces were there, not joined. The Claude Code adapter's `stop()` keeps the config volume and its `resume()` starts a new container on the same session (B5.1a; verified with the real harness on 2026-10-21, [adapters.md](../adapters.md)); the checkout is a host bind mount, so it outlives any container; the ticket's cost already read a lower running total as a new process (P211). But a runner that died was `RUN_ERROR` `runner_exit`, which the flow answers by putting the ticket back; and `startSession` refuses a session that still has containers or networks, which a killed session container leaves (its egress, its test services, its siblings, both networks), so a bare `resume()` after a kill fails.

**Decision.**
1. **Where the state lives.** In the flow engine, on the service's side, as for the sessions the idle watchdog stops: the session's id, its `StartInput` (its checkout, model, policy and tools), its phase and its events stay in the engine and the ledger while its container is gone. Nothing moves into the container or out of the harness.
2. **What a lost container is.** The adapter says it: the attached `docker start` ends with no exit line from the runner while no `stop()` runs, which is how a kill, the kernel's out-of-memory killer or the Docker daemon going away end it. That is a new `RUN_ERROR` code, `container_lost` (`CONTAINER_LOST` in `session/contract.ts`), with the exit code in its message. A runner that prints its exit line with a code stays `runner_exit` and is not recreated: it said why, and starting it again would say the same. A removal that `stop()` itself causes is no loss (the new `stopping` flag). The existing adapter test that ended a runner with no exit line now expects `container_lost`, since that is the case it describes.
3. **The recreation.** The engine closes the session at once (so the end of its stream is not read as a failure), keeps it out of the live sessions and in the set the tick never releases, waits, calls the old handle's `stop()` (what the dead container left goes, the volume stays), then the adapter's `resume()` on the same id, journals `cleared.container_recreated` (attempt, limit, how long it waited), supervises the new handle from the last event, and sends the session one message from the flow: its container was recreated on the same checkout, its uncommitted work and its transcript are there, its turn was cut. The thread keeps one numbering: the loss, the recreation, then the session's own words.
4. **The bound.** `CONTAINER_RECREATIONS = 3` recreations per session, whatever ends each attempt; the waits are 5 s, 10 s and 20 s (`RECREATE_BACKOFF_MS`, doubled; `FlowConfig.recreateBackoffMs` for the tests). The loss after the third recreation, or a third attempt whose resume fails, fails the session: `RUN_ERROR` `container_failed` with the reason ("stopped 4 times", or the resume's error), its containers and networks removed by the handle's `stop()`, its config volume removed through the new `forget` dependency (`Docker.removeVolumes`, label-filtered by the session), `session_stopped`, and the ticket back in Todo with the new put-back reason `container_lost`.
