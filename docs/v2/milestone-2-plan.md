## 3. Decisions this replan takes

Numbered after the first plan's fifteen, so the log can cite them. The orchestrator copies each one into [decisions-log.md](decisions-log.md), with its consequences, when the lane that implements it lands.

16. **The front end is React, built by Vite; the service and the app's server are not built.** The owner's decisions of 06:29 and 06:30 are applied by the React port, merged as pull request 184, whose log entry states the facts: React 19, CopilotKit 1.77.2 through its headless entries only (no runtime, no Copilot Cloud, no public key, every telemetry opt-out set, the web inspector replaced by an empty module, a test that no request leaves the app's origin), shadcn/ui components copied into `v2/app/web/components/ui/` on Radix and Tailwind 4, Phosphor icons in the regular weight, Vite 8 bundling `v2/app/web/` into `v2/app/dist/`, which git ignores and the server serves from the build manifest; `npm test` and the CI build first. The screens keep the kit's identity: the same tokens and markup, Geist, no gradient, the four reference captures as before. The pure parts of each screen (its model) stay under test with `node --test` in `v2/app/test/`; the component tests run under Vitest in `v2/app/web/test/`, rendered to HTML with `react-dom/server`; a later app lane adds its tests in those two places and nowhere else.
17. **Clickable answers keep AG-UI's format.** A question a session or the lead asks is the `cleared.question` CUSTOM event, whose questions carry Claude Code's `AskUserQuestion` shape (header, options with label and description, multiSelect). The React screens render it through CopilotKit's headless hooks as the thread's interrupt, as buttons plus a free answer; the answer goes through the app's answer routes (anti-forgery token, origin), never through a CopilotKit run. The lead's rule from the on-hold branch is kept: two to four options when the question allows it, the recommendation first with "(Recommended)" at the end of its label, no "Other" option.
18. **A workspace is several services; a ticket belongs to the workspace.** Two tables, owned by the store: `workspaces` (id, name, created at) and `services` (workspace, name, kind `repository` or `folder`, repository `owner/name`, url, base branch, path for a folder of a monorepo, health url, sensitivity, consumes, run, contract, created at). A ticket's per-service parts are `ticket_services` (ticket, service, branch, pull request, state). The `project` column of every existing table keeps its name and now holds the workspace id; no v1 table changes (`tracker_*`, `runs`, `events`, `releases`). Reason: the local tracker and `merge-pr.sh` read `project` as it is, and a rename would touch every query for a word. The TypeScript names say `workspace`. A one-service workspace needs no new file: the service builds it from the milestone 1 environment (`CLEARED_V2_PROJECT`, `_PROJECT_DIR`, `_REPO`, `_REPO_URL`, `_BASE`), with the old `project` value as its id, so the guestbook becomes a one-service workspace on its first start after the migration and every existing row stays in it. A workspace of several services is described by one file named by `CLEARED_V2_WORKSPACE`, in the format of `agents.conf` (`[workspace] id` and `name`, one `[service <name>]` section per service with the columns above, plus `broker_socket` and `broker_state` of decision 21); its id is the `project` value of its rows, so the proof's file gives the guestbook's old project name as the id and the guestbook's tickets stay reachable. `FlowConfig` gains a `workspace` field holding the workspace and its services; its existing `services` field (the `[session] services` test containers) keeps its name and meaning. Each service repository keeps its own `.cleared/agents.conf`, read at its base branch, as today.
19. **The store is migrated by versioned, tested migrations.** A table `v2_schema` (version, applied at) and an ordered list in `v2/src/store/migrations.ts`, applied in one transaction each by `applyTables` in `store/db.ts`, right after the module tables are created, so `main.ts` is not edited. Before the first migration of a start, the store writes a consistent copy of the database with `VACUUM INTO` (a file copy of an open database and its WAL is not consistent) as `ledger.db.before-<version>-<time>` next to it, in the 0700 state folder, then sets the file to 0600 (the statement writes with the process's umask); a start interrupted between the copy and the migration leaves a copy that is never overwritten, since the name carries the time and `VACUUM INTO` refuses an existing target. The copies hold the whole ledger: the code never reads or removes them; the owner removes them by hand once the migration is trusted, as brief rule 4 asks for any deletion of data. A migration is idempotent and tested against a fixture ledger made by the schema before it (the fixture SQL is committed under `v2/test/store/fixtures/`), run twice, and the v1 reader of the tracker tables (`lib/tracker/adapters/local.mjs`) still reads it. Milestone 1's rule that a module creates its tables with `CREATE TABLE IF NOT EXISTS` stays: the new tables are module tables, and a migration changes what exists (a column added, rows filled).
20. **One checkout per ticket and per service; the other services are siblings, real or fake.** The workdir of a session is `<workdirs>/<ticket>/<service>`, a clone of that service's repository on the ticket branch (the same branch name on every service the ticket touches); for a folder of a monorepo, the clone is the repository and the session's `cwd` is the folder. The other services of the workspace reach the session's internal network as sibling containers: a real one, or a fake. A real sibling is built in two layers, so that no instruction written by a session ever runs during a build and no build reaches the network: the base layer is the service's own `run` Dockerfile (a path and a port, as the guestbook's `Dockerfile` already allows) built by the service from the service's base branch, reviewed and landed code, as the deploy watcher builds it today; the ticket layer is Cleared's own generated Dockerfile, `FROM` the base layer and a `COPY` of the checkout at the ticket branch, built with `--network none`, with no `RUN` step from the branch. A ticket that changes the dependencies cannot be built that way: the build fails, the sibling falls back to the fake, and the release card's `dependency` flag says why. The fake, also used when the service declares no `run`, is generated from the service's contract (`contract = openapi:<path>`, OpenAPI 3 only in this milestone, the owner's decision of 08:27 on question 5, JSON Schema, protobuf and events coming in milestone 3: each operation answers its first example, or a 501 with the operation's name when it has none), run by Cleared's own labelled `cleared-v2-fake` image. These siblings are the ticket's trial environment. The Browser tab reaches the session's own `run` sibling through a service route (`/api/sessions/:id/preview/*`) whose every response carries `Content-Security-Policy: sandbox allow-scripts allow-forms` and no cookie; the app serves it from a separate loopback origin, a preview listener on `127.0.0.1` (`CLEARED_V2_PREVIEW_PORT`, 8794 by default, checked with `ss -ltn`) that holds no session, forwards neither the owner's cookie nor the anti-forgery token, strips `Set-Cookie`, and is shown in a sandboxed iframe. The listener reaches the service route with the app's own proof of milestone 1 (the shared secret the app already holds), never with anything of the owner; a preview address carries a per-session unguessable segment the service issues when the session starts and the app reads from the session JSON, so a preview on loopback is not found by guessing a session id. The app's `Content-Security-Policy` gains `frame-src <preview origin>`; that origin is `CLEARED_V2_PREVIEW_ORIGIN` when set (the https address of the README's proxy, for a browser on another device, as `CLEARED_V2_APP_ORIGIN` names the app's), else the loopback address, in which case the Browser tab works on this machine's browser only and says so. The proofs' headless browser runs on the server and is not affected. So a page the session wrote runs with an opaque origin, on another origin than the app, without the owner's credentials: it cannot approve anything (brief rule 5, section 5.9), and lane 20 proves it.
21. **The lock stays per service; the train lives in the v2 service.** A release broker runs per service, each with its service's `ORCH_REPO` and `agents.conf`, declared per service in the workspace file (`broker_socket`, `broker_state`; the one-service case keeps the milestone 1 socket and state folder). The brokers share one ledger: each is started with `ORCH_LEDGER` naming the v2 store's file, so `merge-pr.sh` finds the ticket, the review run and the secret's check in the same tables the service writes; each has its own state folder (`CLEARED_STATE_DIR`) for its secret, its `merge.lock`, its merge queue and its validations, since a broker rewrites the secret at start and two brokers in one folder would overwrite each other's. The v2 service keeps `release_trains` (ticket, services in landing order, state per service: `waiting`, `merged`, `healthy`, `failed`, `reverted`): the landing order is providers before consumers from the services' `consumes` lines, then position; each landing is `request_release` on that service's broker, waited to exit 0, then the service's watch read from its ledger until a healthy verdict, before the next; a failing watch rolls that service back by its own `auto_rollback`, and the train then asks `request_rollback` of each earlier landed service, newest first. The compatibility check before approval: a ticket that changes a service's contract file without a step on every service that consumes it is blocked on the card, with the proposal to extend the contract or keep it backward compatible; the owner can still ask the lead to add the missing step. The broker accepts `request_rollback` from the configured human account only (`serve/release-broker.mjs` line 143), and the setup command already names the service's account as `human_user` (`v2/src/cli/setup.ts`), so no broker change is needed: lane 16 verifies it in its real run and edits nothing under `serve/`.
22. **The session plan is validated before the code, with a confidence.** The author's first turn ends with a host tool call `propose_session_plan({ steps, files, confidence: 'low' | 'medium' | 'high', reason })` (the author now has host tools, lane 4), journaled as `cleared.session_plan`; the flow holds the author until a Go: the owner's, from a `session_plan` inbox item ("Go", "Change" with a message that reopens the author); or the delay's, `[session] plan_go_minutes` of the service's `agents.conf` (10 by default), after which a high-confidence plan starts by itself and a medium or low one keeps waiting; or the lead's, for a ticket of an approved plan with a high confidence, since the owner approved that plan. A reopened author after a review does not propose again. The measured step is `plan_gate`, counted apart from working time.
23. **The release request is grouped by intent, with flags.** At the end of its work the author calls `report_changes({ groups: [{ intent, files }] })`; the service checks every changed file is in exactly one group (the rest go to "Other changes"), and computes the flags from the diff: `schema` (a migration folder or `.sql`), `dependency` (`package.json` dependencies or the lock file), `config` (`guarded_paths`, `.github/`, `.cleared/`), `secret_shape` (a line the guard would flag, which also refuses the publish), `contract` (a service's contract file), `large` (more than 400 lines added). The card shows the groups with their files and the flags; a flag is a chip, never a block, except `contract` on an untouched consumer (decision 21).
24. **Sensitivity per service, flagged from the plan.** `sensitivity = normal | full | reviewer:<model> | human:<user>` on a service: `full` refuses the fast lane for any ticket touching it (a fast plan item becomes full with a note); `reviewer:<model>` makes that model the reviewer of the ticket's sessions on that service (another model than the author's, else refused at configuration); `human:<user>` adds that user as the one who must approve the release (the signed-in owner's approval is refused for another user, with the message naming who). The plan panel shows a sensitivity chip on each item from the services its body names, and the lead's rules say it.
25. **Memory has three levels: workspace, service, contract.** `lib/memory` is run three times, each in its own state directory: `<state>/memory` (the workspace), `<state>/services/<name>/memory` (each service), `<state>/contracts/<name>/memory` (each contract, named by the service that provides it). The briefing of a session on a service reads the workspace page, then that service's page and lessons, then the pages of the contracts its ticket touches, within the same byte budget; a handover files its lessons in the level the author names (`## Lessons for the service`, `## Lessons for the contract`), else in the workspace's. The lead's briefing reads the workspace level and the service pages' first lines.
26. **A ticket runs in steps.** `ticket_steps` (ticket, kind `contract` | `service` | `integration`, service, position, after, state, session, cost): the contract step is a session on the providing service that changes only the contract file and ends with the contract's diff proposed as an inbox `contract` item (Approve, Send back); the service steps run after it, in parallel, each with the fakes of decision 20 (the fake of a changed contract is built from the validated one); the integration step runs last on the consuming service with every sibling real, and its tests are the ticket's criteria. A one-service ticket has one `service` step and nothing else changes. The lead's plan items gain `steps`, with a cost per step from the estimates (lane 7's medians by size, per step kind); the plan shows the steps' order and dependencies.
27. **Knowledge is proposed, then approved in the inbox, then landed in the skill.** A handover's lessons and the decisions it names become `knowledge` inbox items (text, level, source session), with Approve and Reject; approving writes the entry into `lib/memory` at its level at once (the next briefing has it), and queues it for the service's skill; once a day, or on the owner's "Update the skill now", a fast-lane ticket per service writes the queued entries into `.claude/skills/cleared-<service>/SKILL.md` in the standard skill format (front matter `name`, `description`; the body in sections per level), through the lock like any change. The approval-by-comment of v1 is not carried over. The project's skills under `.claude/skills/` are mounted into the session as they are, read-only, by lane 15 (milestone 1's lane 5 named it; nothing of it exists in the code on 2026-10-22).
28. **A read-only question to the code, or to the platform, with its cost.** A `reader` role: a session on the base branch of the named service (or, for the platform, on a workdir holding every service's checkout, read-only), with the reviewer's policy (no edit, no commit, no push), briefed with the question, which may name a service, a file and a line (`service:path:line`; the briefing adds the file's lines around it); started from the tower bar ("Ask about the code") or a session's Plan tab, shown on a `/ask/:id` screen with the answer, its cost (`total_cost_usd`, tokens, and the week share when measured) and a follow-up field; stopped by the idle rule. It is never a plan item and never writes.
29. **Recipes live in the repository; schedules live in the store.** A recipe is `.cleared/recipes/<name>.md` in a service's repository (front matter: `name`, `kind: ticket | goal`, `parameters`, `lane`, `size`, `services`; the body is the ticket's body or the goal's text with `{{parameter}}` marks), read at the base branch; the tower bar lists them ("Run a recipe") and runs one as a one-item plan (a ticket) or an owner turn to the lead (a goal). A schedule is a row of `schedules` (recipe or goal, `at` or `every` in the server's time zone, budget in USD, week-share cap, created by, enabled): the scheduler ticks each minute and starts the run through the plan runner, with the creator's approval given at creation as the plan's approval; the ticket's budget is the schedule's; a release still waits for the owner; the week stop still wins. The tower's plans card lists the schedules and their next run.
30. **The session screen has four tabs, and the owner can take over.** Plan (the session plan with its confidence and Go, the criteria, the steps of the ticket), Terminal (milestone 1's live timeline and the message field; once the session is taken over, the web terminal of decision 32), Editor (the changed files with their diffs and a file viewer of the checkout through a service route with the events' cleaner and limits, editable by decision 33), Browser (the trial environment of decision 20, else milestone 1's "Screen so far" capture). "Give back" closes the terminal, tells the session what the human changed (decision 33) and resumes it with the harness's `resume` in the same container. This is brief 5.10's "Open in terminal" and "Give back to Cleared".

A lane that passes 5 points of the week is stopped and analysed, as brief section 4 says.
32. **The web terminal: the human types into the session's container, with Take over and Give back** (owner decision of 08:27, question 3, option (b), in milestone 2 by the owner's request for an addendum to milestone 2 if this changes the split). It opens only on a session taken over (decision 30) and closes on Give back, so the human and the harness never type at once. What it runs: a shell (`bash -l`) in the session's own container, as the session's user, in the checkout; its first line shows the command that resumes the harness inside it (`claude --resume <id>`), which the human may run. The shell has exactly the container's reach (the egress allow list, no Docker, no forge credential, the read-only image), so a push or a deploy from it fails as one from the session would. The transport is the app's own, with no new listener and no WebSocket: the output streams to the browser as server-sent events (`GET /api/sessions/:id/terminal/stream`), through the streaming proxy the session's events already use; each keystroke batch is a `POST /api/sessions/:id/terminal/input` (at most 4 KiB), with `open`, `resize` and `close` as posts too. Reason: a browser cannot put the anti-forgery header on a WebSocket handshake, and the posts reuse the app's write checks unchanged. The service runs the shell with `docker exec --interactive --tty` through `container/docker.ts`, under its label rule (the container id from a labelled list, after `--`); the CLI needs a terminal for `--tty`, and the candidate is the host's `script` (util-linux) around that command line, built from fixed words and the owned id only, never from what the human types, which goes to the process's input (section 8 holds the unknown). The safety rules are the orchestrator's requirements for this addendum, not the owner's words; each has its test in lane 31:
    - **The authenticated owner only.** The users module has no role, so in milestone 2 Take over is limited to the single owner account: the first account of the users table (the oldest `created_at`, the one setup creates). Take over by any other signed-in account answers 403 and says why, so a second account added later does not silently get a shell in a session's container; roles, deciding who may take over which session, come in a later milestone with the several users of the owner's decision of 2026-10-21. The owner is then the signed-in app user who took the session over, recorded by Take over, and the editor's saves are limited the same way. The app requires the session cookie for every terminal route; the service requires the app's proof and answers only that user, and refuses the flow's own identity (`cleared`) and the lead's.
    - **Anti-forgery and origin.** Every post carries the anti-forgery token and the app's own `Origin`, as any write (`app/src/server.ts`); the stream needs the cookie and, when the browser sends it, `Sec-Fetch-Site: same-origin`.
    - **Loopback only.** Nothing new listens: the terminal rides the app's and the service's loopback listeners. The app answers the terminal routes only when the request reached it on its loopback address (a `Host` of `127.0.0.1` or `localhost` at its port, with the matching `Origin`), never through `CLEARED_V2_APP_ORIGIN`; `/api/me` tells the page whether the terminal is offered, and on the public origin the Terminal tab shows the command of decision 30 and says the web terminal opens on this machine's browser only, as the Browser tab does.
    - **No agent session can reach it.** A session container reaches neither the app nor the service (milestone 1's egress rule and its test); no host tool of the lead or of an author names a terminal route, and a test lists them; a page on the preview origin of decision 20 has no cookie and another origin, so its posts are refused; what the human types never enters a model's context.
    - **Everything typed is journaled.** The input is journaled line by line, at each Enter and at close for the rest, as `cleared.terminal_input` with the user and the time, each line through the events' cleaner as a whole, so a secret typed in several posts is masked; `cleared.terminal_opened` and `cleared.terminal_closed` (with the byte count of the output) frame it. The output is never stored, since it can hold file content (brief 5.2).
    - **Its limits.** One terminal per session at a time; closed after 15 minutes without input, the session staying paused until Give back; Give back ends the exec's process before `resume`.
33. **The Editor tab is editable, and the session is told of the human's changes** (owner decision of 08:27, question 4, option (b)). A save is `PUT /api/sessions/:id/files/*` with the text and the hash of the version the editor loaded; it is allowed while the author's session of a ticket in progress is live or taken over, and refused while the review runs, after the publish, and on an ended session. The check goes through the same path rules as the session's edits, on the host: first the files route's own refusals (outside the checkout, `.env` and the guard's secret names), then `evaluate()` of `session/policy.ts` with a `Write` request under the author's policy for that session. The request names the file by its path inside the container, since `Policy.workdir` is the checkout's mount point there, and `PolicyContext.readFile` is given the file's current text, read in the container as below, so an edit of `package.json` is judged on what it changes, not answered `unknown`. An `allow` writes; a `deny` refuses with the rule and its reason. An `ask` is confirmable in the editor for two rules only, `install.package` (a dependency of `package.json`, the lock file) and `scripts.change` (the scripts of `package.json`): the editor shows a confirmation naming the rule, and a second save carrying that rule writes and is journaled as that user's answer "once" to it, as the inbox would record it. An `ask` for any other rule, `default` included, is a refusal: `.git/**` (run by git on the host), `.claude/**` and `CLAUDE.md` have no rule that allows them, so `evaluate()` answers them `ask` with `default`, and a confirmation would let one click write a git hook the service's own git runs outside the container. The write itself happens inside the session's container, not on the host: the service runs a fixed program of its own code with the image's `node`, through the docker wrapper's existing `exec` (the container from a labelled list, after `--`, as the container's user, the session's), with the path and the loaded hash as arguments and the text on its input; the program checks the hash, writes a temporary file in the same folder, then, after creating that file and before the rename, resolves the target's real path inside the container (the parent folder's real path, and the file's when it exists) and refuses the save, removing its temporary file, when that real path leaves the checkout, lands in a `.git` or `.claude` folder, or names a `CLAUDE.md`; only then does it rename. Reason: the session may be live and may swap a parent folder for a symbolic link between a check on the host and a write on the host; inside its container the kernel confines the write to what the session's own `Write` reaches, and the read-only mounts (the login, the image) refuse it. The kernel does not protect `.git/**`, `.claude/**` and `CLAUDE.md`, which the policy protects by the words of the path: a link the session made inside the checkout (`scripts -> .git/hooks`, `notes.md -> CLAUDE.md`) would turn the owner's save of `scripts/pre-commit` into a git hook the service's own git runs on the host, so the program checks the real path the rename will write, not the path the owner named. A save never calls a file write of the host. Text only (UTF-8 with no NUL), a file the viewer cuts at 400 lines is read-only, and a hash that no longer matches answers 409 with the current one, so a file the session changed before the save is reloaded, never overwritten; a change the session makes in the few milliseconds between the program's hash check and its rename is lost, and the notice below tells the session to read the file again (section 8). Each save is journaled as `cleared.human_edit` (the user, the path, the lines added and removed, the hashes before and after, `via: editor`), never with the content. The session is told: while it is live, at once, through the engine's `send` ("<user> changed these files: <path> (+a, -r). Read them again before editing them."); while it is taken over, at Give back, in one notice with the files the terminal changed, found by comparing the checkout's `git status` and `git diff --numstat` at Take over and at Give back and journaled as `cleared.human_edit` with `via: terminal`. The change is part of the ticket's branch, so the reviewer, the guard at publish and the release card see it as any change, and the reviewer's prompt names the files a human changed, through `flow/human-edits.ts` (lane 23 places the call with an empty default, lane 31 fills it).
