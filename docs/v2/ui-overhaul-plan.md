# Cleared v2: the native interface overhaul, planned

On 2026-10-22 at 22:01 (Europe/Paris) the owner, after using the demo instance for an evening, found the interface dreadful: not modern, not practical, too many loads between the tabs; the author to reviewer transition is not smooth; Take over is impossible on the reviewer (delivered since by pull request 242, lane `v2-j2-takeover-real-harness`, which records that part of the feedback as O19; this plan draws it and does not implement it); the inbox shows a permission request as a raw chained shell command with an English reason and no button, under items that no longer wait. The owner wants the look and feel of a native application and gave carte blanche for the night. At 22:04 the owner named the references: the interfaces of OpenAI Codex (the web and desktop apps) and of Devin, with Linear and Raycast as secondary references, and asked that the interface lanes use Impeccable for their audits, critiques and polish. This page diagnoses the interface screen by screen on captures of the live app, states the requirements, and plans six lanes in order (a small dependency lane and five interface lanes), the data and routing foundation first. The requirements matrix records the feedback as O20 and the precision of 22:04 as O21 (O18 and O19 are taken by pull requests 240 and 242). It contains no code: every lane writes its own, tests first, as [milestone-2-plan.md](milestone-2-plan.md) section 4 asks.

Written on 2026-10-22 by a Fable 5.1 planning session (logged in [decisions-log.md](decisions-log.md)). Inputs: the owner's feedback of 22:01 and precision of 22:04 (in the log); the `v2/app/web/` code at `origin/v2` commit `d0e5e0e` (the head of the demo and of the proof instance, both read on this server); the captures under `docs/v2/ui-overhaul/before/` (section 1.1); the public documentation of the four references (section 3); Impeccable's repository and package (section 6). Every file, route, number and version below was read or measured on this server on 2026-10-22 between 22:05 and 22:40; "unknown" marks what was not verified.

### 1.2 What every screen shares: a page per tab

The React port (lane 12) kept the shape of the pages it replaced: the app's server answers each address with its own HTML page whose `<body data-screen>` names the screen (`v2/app/src/server.ts`, `PAGES`), and the shell's header draws the tabs as plain links (`v2/app/web/shell/Header.tsx`, `tab()` renders `<a href>`). Each click on Tower, Inbox, Sessions or Plans is therefore a full document load. What then happens on every page, read in `v2/app/web/shell/App.tsx`:

1. the bundle and the screen's chunk load (cached after the first page, but parsed and executed again);
2. `App` fetches `/api/me`, then the inbox count (`/api/service/inbox`) and the lead's state (`/api/service/lead`), and polls both every 15 seconds (`INBOX_MS`);
3. the screen renders nothing (`Suspense` fallback `null`, every screen returns `null` until its data arrives), then fetches its own data: the tower every 10 seconds (`REFRESH_MS`), the inbox every 10 seconds, the session its siblings every 10 seconds, the lead and the session their AG-UI streams through CopilotKit;
4. the scroll position, the open tab, the composer's draft and the terminal's buffer are lost with the page.

Measured on the live app (loopback, headless Chromium, four runs at 1440 light, 1440 dark and 390 dark; "content" is the time from the click to the screen's first node being present and not busy, the range over the runs):

| Navigation | How | Document loaded | Content present | Requests |
| --- | --- | --- | --- | --- |
| Tower | address or header link | 24 to 99 ms | 135 to 409 ms | 25 |
| Inbox | header link | 22 to 65 ms | 130 to 531 ms | 23 |
| Sessions index | header link | 28 to 157 ms | never: blank (section 1.4) | 22 |
| Plans (the lead) | header link | 18 to 27 ms | 200 to 233 ms | 23 |
| A session | address | 25 to 37 ms | 162 to 284 ms | 25 |
| Session tab Plan | tab button, in page | no load | 67 to 73 ms | 0 |
| Session tab Editor | tab button, in page | no load | 62 to 82 ms | 3 |
| Session tab Browser | tab button, in page | no load | 54 to 69 ms | 0 |
| Session tab Terminal | tab button, in page | no load | 59 to 82 ms | 0 |
| Author to reviewer | the crumbs' link | full load | 216 to 247 ms | 25 |

On loopback the numbers look small; the owner's path is a device on the tailnet through the HTTPS front, where each of the 22 to 25 requests pays a round trip, and the blank between the document and the content is what the owner sees as "a load between tabs". The in-page tabs of the session screen, which do not reload, are under the 100 ms budget already: the budget is reachable once every switch is an in-page one.

## 2. Requirements

Each requirement names its proof; section 4's lanes carry them.

### 2.1 (a) Zero reload between tabs and screens

1. One document for the whole app: the server answers every screen address with the same shell page, and a client router draws the screen (`U1`). A test on the app's server proves the five addresses, the session's and the plan's addresses answer the same page, and that an unknown address still answers 404.
2. A shared data cache, one entry per resource (`sessions`, `session <id>`, `tickets`, `inbox`, `lead`, `workspace`, `steps <ticket>`), read by every screen and the shell (`U2`); the inbox count and the lead's pill read the cache, they poll nothing of their own.
3. The cache is fed live by one SSE stream of the service (`GET /api/events`, `text/event-stream`, read by an `EventSource` at `/api/service/events` through the app's proxy, the session cookie required; `U3`): each event names a resource that changed, the cache refetches that resource, nothing else. The thread of a session keeps its AG-UI stream. When the stream drops, the `EventSource` reconnects by itself, the cache refetches everything once on a reconnect, and until the stream is back the cache falls back to the polling intervals of today.
4. Prefetch on intent: hovering or focusing a link to a session or to a screen prefetches its data and its chunk; a session row in the tower or the inbox is warm when clicked.
5. Session views stay mounted: a session opened once keeps its component, its terminal and its editor alive while the person visits other screens, up to the five most recent (`U4`); the terminal's scrollback and the editor's unsaved text survive a visit to the inbox and back. The terminal and the editor are never recreated by a tab or screen switch (a test counts their constructions).
6. Optimistic updates for the gestures a person makes in the lists: answering a permission, a question, Go, approving a release, sending a message: the list moves at once and reconciles with the event.
7. Skeletons on the very first load of a resource only; afterwards the cache's last value is drawn and refreshed in the background. No full-screen spinner anywhere (a test greps the built bundle's sheets and markup for a page-level busy state).
8. Budget: a tab switch is under 100 ms, measured as the time from the click to the next screen being painted with its data from the cache, as the median over three runs of the p95 of twenty switches, in a browser test on the fixtures source, in CI (`U5`); a switch makes zero document navigations and at most one background request.

### 2.2 (b) The look and feel of a native application

1. A persistent sidebar replaces the header's tabs: the workspace at the top, Tower, Inbox (with its count), Sessions, Plans, Tickets later, the lead's state as a dot, the person and the theme at the bottom; collapsible with a shortcut; the current screen marked. The references' layouts are in section 3.
2. A command palette on Cmd-K (Ctrl-K elsewhere): screens, sessions by ticket and title, the inbox's waiting items, the gestures of the current screen (Take over, Give back, Go, Approve, Answer), the theme, the shortcut sheet. Built on the `Command` component of shadcn/ui, which wraps cmdk.
3. Keyboard shortcuts everywhere: G then T, I, S, P for the screens; J and K in every list, Enter opens, Esc backs out; 1 to 4 for a session's tabs; Cmd-Enter sends a message; `?` opens the sheet. Every shortcut is shown in the palette and on hover.
4. Density under control: list rows of 32 to 36 px, a 13 to 14 px type scale for the lists and the thread (the references use 14 px), the monospace for commands and paths only; the tower's cards become rows with a kind, a title and one line.
5. Typography and spacing from tokens: a four-step spacing scale, three text sizes and two weights in the app's sheet, and nothing else; Geist stays.
6. Transitions short (120 to 160 ms, opacity and transform only), respecting `prefers-reduced-motion`.
7. Empty states that say what to do, with one action: an empty inbox, no session, no plan, no changes yet.
8. Dark and light flawless: every token has both values, contrast checked by Impeccable's audit at AA for text, the capture loop at the four widths in both.
9. shadcn/ui and Phosphor stay the component library and the icon set; no new icon set, no new component library.

### 2.3 (c) A smooth author to reviewer transition

1. The session view follows the ticket, not the session id: when the reviewer starts, the same view shows a handover row in the thread ("Reviewer (Sonnet) took over at 22:31; the author's work is above"), then the reviewer's thread continues below, live, from its AG-UI stream; the Editor already holds the author's diff (it is the ticket's branch); the Checks go on. No navigation, no reload, no spinner (`U6`).
2. The address stays shareable: `/sessions/<id>` opens the ticket's view at that session; while the reviewer runs, the address is replaced (without navigation) by the live session's, so a reload lands on the live one. The crumbs' Author and Reviewer become a filter of the thread, not links.
3. A discreet notification: the handover row itself, the sidebar's dot on Sessions and the palette's "Waiting for you" section; no toast, no sound. Web push stays the service's decision, as today.
4. Take over on the reviewer is pull request 242's (lane `v2-j2-takeover-real-harness`, O19): the service takes over an author's or a reviewer's live session, Give back resumes the review and tells it of the human's edits, and the screen offers the button on both roles. This plan draws it in the ticket's view: the Take over and Give back of the live session of the thread, whatever its role, in the same place, with the handover copy of 2.3.1; no file of the takeover is edited (`U7`).

### 2.4 (d) No slop

No gradient but the grace bar's fill, no emoji, no decorative illustration, no filler copy ("Welcome back!", "Let's get started"), no exclamation mark in the app's words, no sentence that explains the interface to itself. A test keeps `linear-gradient` out of the app's sheets but one named class, and the art director's pass reads every catalog sentence against the copy rules of section 5.

### 2.5 (e) The inbox's permission requests, and the French

1. **A clear French title that says the intent**, written by a pure function from the command: known shapes are classified ("Lire l'historique et le diff du dépôt", "Lancer les tests du projet", "Installer une dépendance", "Appeler le réseau", "Lire le dépôt et lancer les tests" for a compound of two classes); an unknown command gets its first word and an ellipsis as a title ("docker ..."). The function's table of shapes is its test's table.
2. **The raw command folded** under the title, in monospace, one command per line for a compound (split on `;`, `&&`, `||` and `|` for display only, never for the decision).
3. **The reason translated.** The service adds a `reasonCode` to a request beside its `reason` text (`compound`, `not_allowed`, `network`, `dependency`, `outside_checkout`, `unknown`), set by the policy lane; the inbox translates the codes it knows ("Le merge-base git n'est pas une commande que la politique autorise seule" for `not_allowed` with the command's name) and shows the service's English text in the fold when the code is `unknown` or absent. The policy lane owns the codes' values; this plan fixes the field's name and the app's fallback so neither lane waits for the other.
4. **The buttons on the item**: Autoriser une fois, Toujours pour ce projet, Refuser, clickable on the list row at 1280 and above and at the top of the detail, before the fold, at every width; the sticky bar of today stays for the release and plan items.
5. **A folded "Traité" group**: what was handled and what expired (a request its session's end closed) sit in one group, collapsed by default with its count, below everything that waits; opening it shows the items with a lighter weight; a handled item's title keeps its intent sentence.
6. **The whole interface in French when the language is fr**: a test renders every screen, the sign-in page, the palette and the shortcut sheet in fr on the fixtures and asserts no English catalog fallback is drawn (the translator throws no more; it marks a missing key, and the test fails on any mark); the words the service writes (a ticket's title the lead wrote, a check's name, a session's report) are shown as they are, under French labels.

## 4. Decisions this plan takes

Numbered `U` so they do not collide with the milestone plans' decisions; the log entry records them.

- **U1. Client routing with TanStack Router**, in code (no file-based routes), with its intent preloading and its typed search parameters; the server answers one shell page for every screen address and keeps the 404 for the rest. Reason: the router's preload on hover and its pending-state rules are what requirement 2.1 asks, built in; React Router in library mode would do the same with more code of our own. Both are new dependencies, each with its one-line reason in `package.json`, added by the dependency lane (lane 33).
- **U2. TanStack Query as the shared cache**, one key per resource, stale-while-revalidate, the mutations optimistic for the gestures of 2.1.6. The screens' pure models stay; the components read the cache instead of fetching and polling.
- **U3. One SSE stream for the lists** (`GET /api/events`, a service route answering `text/event-stream`, served through the app's proxy at `/api/service/events` and read by an `EventSource`; the proxy already passes the terminal's and the lead's event streams: it writes the headers at once and pipes the body unbuffered, `v2/app/src/proxy.ts`, and the demo's HTTPS front pipes the same way). The stream carries thin events (`{ kind, id, at }`, each with an id so `Last-Event-ID` resumes it) from the flow's bus (`FlowEngine.subscribe`, `v2/src/flow/events.ts`) and from an `onChange` hook the foundation lane adds to the inbox store; no payload, so nothing of a session's content travels on it and the cache stays the one reader of the routes. The service writes a comment line every 20 seconds as a keep-alive, so no idle timeout of a front cuts a quiet stream (the demo's front sets none; a front of its own, as nginx, needs its buffering off and a read timeout above the keep-alive, which the deployment notes say). The `EventSource` reconnects on a close with its own backoff; on a reconnect the cache refetches everything once. The AG-UI streams of the session and the lead are untouched.
- **U4. Session views kept mounted** in a stack under the router: a visited session's component stays alive and hidden, with its terminal, editor and browser frame, up to five, least recently used first; the terminal refits on show. Reason: the owner's "never recreated" for the terminal and the editor cannot hold otherwise; five bounds the memory of a long evening.
- **U5. The budget is measured in CI.** A browser test on the fixtures source switches tabs twenty times, measures each from the click to the next frame painted with data, and fails above 100 ms, above zero document navigations, or above one request per switch. The 100 ms bound is strict and measured as the median of three runs of twenty switches, each run's p95: one slow run on a shared runner does not fail the job, two do; the three runs' numbers are in the job's summary, and the same test runs locally with one run. CI gets a `browser` job with playwright-core and the Chromium headless shell (today the browser tests are skipped in CI without `CLEARED_V2_PLAYWRIGHT`); the measure's numbers are printed in the job's summary and the proof report reads them.
- **U6. The session view follows the ticket.** The route reads the ticket from the session, subscribes to the ticket's sessions, and draws one thread of the ticket's sessions in order with handover rows between them; the reviewer's start arrives by the event stream and continues the same view.
- **U7. ## 5. The visual loop, the art director and the copy rules

Every interface lane runs the same loop, as the milestone plans ask, extended with Impeccable:

1. **Captures** of its screens at 1440x900, 1280x800, 768x1024 and 390x844, light and dark, on the fixtures source, with the repository's capture script (lane 34's), zero page errors and zero requests off the app's origin; the files go to `docs/v2/ui-overhaul/after/<lane>/`.
2. **Impeccable's `audit`** (accessibility, performance, responsive) and **`critique`** (hierarchy, clarity) on the lane's screens, the findings fixed or named in the log entry; **`polish`** last, before the review.
3. **The art director's fresh look**: a Sonnet 5.5 session that has not seen the lane's work opens the captures and the running fixtures app, runs Impeccable's `critique` and `polish` itself, reads the copy against the rules below and against section 2.4, and answers in a list: what to change before the merge, what to log for later. The lane's author applies the first list.
4. **The copy rules**: a sentence says one thing; the app's words are in the catalogs in both languages; a button is a verb; a state is an adjective; no exclamation mark; no "please"; a number has its unit; a time is in the person's language; nothing explains the interface to itself.
5. **The measures**: the browser job's tab-switch numbers before and after the lane, in the log entry.
